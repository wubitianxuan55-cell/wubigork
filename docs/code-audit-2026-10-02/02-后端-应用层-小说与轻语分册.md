### 总评

两个单元的病不是「写得脏」，而是**「同一件事没有唯一实现」**。AP1 的生成链把「下一步该干什么」散成了若干份平行判据：什么算下一章（4 份）、什么算阻断（5 份）、哪条 beat 是当前水位（下标与章号混用）、前文摘要从哪取（4 份）、哪个节点是本章（5-7 份递归遍历）、比对键怎么归一（6 份）。AP2 把「怎么跑一个后台长任务」散成了三份模板与六套在途登记簿。两单元的后果是同一个：**改一处口径，必漏另外几处，且漏掉的那处是静默的**。

并发只占 2 条 P0，但都是「登记纪律没走全」的直接后果：`converge_handler.go:177` 的后台协程既不在取消登记表、也不在 WaitGroup、也不取同章互斥，切书后闭包还握着入口处的 `pm`（`:157`）继续写盘；`scene_cards_handler.go:218` 的逐场景协程只登记不计账，`waitGensDone` 会提前返回，把已在册的 Windows `unlinkat` flaky 从整章生成路径搬到场景路径重新引入。这两条都不是「理论风险」——它们复用的是仓库自己在 `create_chapter_handler.go:237` 与 `create_chapter_cancel_test.go:101-122` 已经写明并修过的纪律。

值得肯定的两条：AP2 的 fail-closed 守卫与原子写盘、以及 AP1 取消残稿的「正文已存在→侧车不覆盖正稿」三态保护，注释与意图都很清楚。问题只在于这些正确做法**没有成为唯一入口**（见第 3.2 节）。所有修法的共同方向是「先建唯一实现，再删平行份数」，而不是推倒重写。

## 五、观察项 / 未定论

来自两单元 open_questions，均未实证，不得当作已确认缺陷：

1. `novel_gate_handler.go:184 findByFile` 优先于 `:200 findByOrder`，而 `create_chapter_context.go` 的 `planPrecheck` 只按 OrderIndex 找节点（`findOutlineNodeByNum`）。同一章在两处可能匹配到不同大纲节点（ChapterFile 指向别章但 OrderIndex 相等），两套写前闸结论是否真的「必然一致」未构造出触发分歧的磁盘数据。
2. `eval_baseline_handler.go` / `eval_corpus_test.go` 未精读，是否又复制了一份章节枚举与内容收集口径（与 `deepListChapters`、`countWrittenChapters`、`convergeCollectUnits` 同族）未核实。
3. `foreshadow_context.go:17` 提到「L5 兜底层承接存量无计划条目」，`foreshadow_handler.go:43` 又有「空 ID 兜底 manual_ 前缀」；伏笔域是否存在与 `novel_foreshadow_lint_handler` 重复的序/状态判据未逐条核对。
4. `scene_cards_handler.go:218` 的协程漏计 WG 是否已在 CI 上真实抖动过（AGENTS.md 只记录了 CreateChapter 真链的 unlinkat），受「不跑测试」纪律限制未实证。
5. `converge_handler.go:177` 的协程在切书场景是否真的会写到已关闭的 `project.Manager`（`pm.Close` 后写入行为）未实证，仅从「不入任何登记/等待机制」推断。
6. sin 工具预算只对「真实存在的工具」扣次数（`sin_tool_loop.go:160-164`），未实机验证恶意/循环模型能否用未知工具名把 `extra.tools` 撑到多大——extra 无总长上限，落库膨胀量未测。
7. `novel_bookcover` 绕过 `mediaState` 后，画室台账里书封的 space/source_board 与章节插图不一致（`gaeaCwd()` 根 + play/novel），未确认前端按来源筛选时书封是否可见。
8. `bookImportRuns` 为包级变量且 jobID 毫秒+序号可枚举，是否存在跨板块误取消的真实触发路径（前端状态错位/双开壳）需真机走查确认。
9. `sin_insight` 的 `Seq=消息ID×10+槽位` 在消息 ID 超过 int64/10 或 chat.store 换用非自增主键时会整体失效，未确认 `chat.store` 主键生成策略是否有长期保证。
10. `sinHandler` 主循环的 5 轮上限与 `sinToolCallMaxTotal=8` 叠加后，正文字数与费用的最坏情况未实测（真机记录只到「12 次工具调用正文几十字」的历史症状）。
