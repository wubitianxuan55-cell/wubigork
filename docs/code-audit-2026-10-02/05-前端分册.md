## 一、板块总评

前端不是一个「代码烂」的板块：测试密度高（FE4 18339 行非测试代码配 9197 行测试、FE6 112 个测试文件 11541 行、FE7 40 个测试文件 7337 行）、三语字典键集完全对齐（1553/1553/1553）、错误可见化与脏守卫这类纪律性地基真实存在。它的病是**结构性重复 + 上帝文件 + 双契约**：同一件事在前端内部实现 2~4 份（LCS diff 四份、genui 白名单三份、绑定清单三份、扩展名五份、打字机流两份、ComfyUI 轮询三份、拖拽三件套三份），同一份数据模型在 TS 与 Go 之间双写而无生成器（FE7 的多基线字段已在真实丢数据）。

最痛的三类，都不是「可读性问题」，而是**用户已经在受损的静默失效**：

1. **静默数据丢失 / 静默失败**：多基线 `baselines` 被 Go 保存链路整字段擦除（FE7-01）、表格视图全选调用未定义函数点击即抛且无反馈（FE2-01）、知识库 phase 过滤恒真（FE1-03）、麦克风不可用静默伪造音量（FE6-02）、genui 校验器把合法 diff/series 规格判非法（FE6-01）。
2. **一句话就能修却长期挂着**：日志通道自身同步抛异常击穿 fallback（FE3-02）、HTTP 代理缺 then 守卫（FE3-08）、空间门控 fail-open（FE3-06）、`isProjectOpen` 死字段（FE1-15）、`_running` 死参数（FE1-12）、`destroyOnClose` 弃用名（FE2-16）。
3. **上帝文件封顶了后续所有改动的成本**：CostLibraryView 1132、CreatePage 1500、ChapterPage 1188（FE5）/1117（FE6 口径）、WeixinPage 1034、CharacterPage 1006、ModuleLauncher 1038、App.tsx 1041、controller.ts 874、useImageGenConfig 357。

## 五、观察项 / 未定论

1. **`743` vs `745` 口径**：FE3 open_questions 实测 `bindingNames.ts` 共 745 行、名字 743 个；FE4 hotspot 记 746 行。建议汇总层以 **743 个绑定名**为口径，行数差为文件行数混淆，不必再查。
2. **`makeMockApp()` 覆盖度未证伪**：16 个 builder 各自只声明 Pick 子集，`Object.assign` 后直接 `as AppBindings`，无断言保证每个键都被提供（FE3 观察项）。若无法给出反例则为洁癖项；加一条「`Object.keys(makeMockApp())` 覆盖 AppBindings 全部短名」的测试即可定性。
3. **`KnowledgeSummary.phase` 是后端不返回还是前端漏声明**：FE1-03 只读前端，需读 `internal/app` 知识库 handler 确认；两种情况的修法不同（补类型 vs 改过滤通道）。
4. **`api/` 直调面规模未知**：`api/engines.ts:365` 的 AppFacade 索引签名让大量绑定名落在 `drift.ts` 两把类型锁之外，具体还有多少项、是否有生成期核对需与后端单元交叉（FE3 观察项）。

9. **`pages/sin/`（20 文件 4300+ 行）与 `pages/modelcenter/`（23 文件 5500+ 行）未逐字精读**：前者疑似有与 CreatePage 同族的第二套流式编排，后者「一 section 一 hook」可能是正向范式，均需后续单元。
