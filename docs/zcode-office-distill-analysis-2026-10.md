# 分析篇：ZCode 蒸馏八份子报告的交叉校验与优先级重排

> 前置：[调研与论证](zcode-office-distill-2026-10.md)（结论层）· [八份子报告](research/zcode-distill/README.md)（证据层）
> 日期：2026-10-24 · 状态：分析，未改任何代码
> 方法：把 8 份报告当作 8 个独立证人，做**交叉校验**（同一事实多方陈述是否一致）、**依赖分析**（谁的结论以谁为前提）、**证据分级**（哪些能进决策，哪些只能当线索），最后重排优先级并回头修正第一版文档。

---

## 0. 这篇分析解决什么

第一版文档把 8 份报告"收敛"成 20 条蒸馏项，但收敛过程中丢掉了三样东西：

1. **分歧**——报告之间互相矛盾的地方，被平均掉了；
2. **前提**——某些项看起来是 S 成本，实际被另一层的前提卡住；
3. **时效**——有报告把 gaea 的能力读旧了（例如"上下文条完全空白"），照抄会重复建设。

所以这篇做三件事：**裁决分歧、找出隐藏依赖、修正结论**。结论是：第一版的 20 条蒸馏项 + 9 条不采项里，**7 处要改**——2 处换理由、2 处成本重估、1 处降证据强度、1 项移出不采清单、1 项明确不采纳；但主方向（工艺 + 门禁 + 锚点）不变。

---

## 1. 八个证人，三种"办公板块"

把 8 份报告的隐含问题意识摆在一起，会发现它们其实在回答三个不同的问题：

| 层 | 问题 | 报告 | 结论（成熟度） |
|---|---|---|---|
| **运行时层** | 这个 agent 跑得稳不稳、可不可控 | s1 · s2 · s5 | **gaea 已超越 ZCode**（compact 阈值更细、四道终局闸、证据链、Plan→Apply） |
| **产出层** | 交出来的文件像不像人做的 | s7 · s8 | **ZCode 明显更强**（场景手册、阈值表、机检规则） |
| **感知层** | 用户与模型是否在看同一版 | s3 · s6 | **两边都缺**，gaea 缺在"指认"，ZCode 缺在"办公用户的简化" |

这个分层解释了一个此前的困惑：为什么"蒸馏 ZCode"听起来像"学一个编程 agent"——因为 s1/s2 是体量最大的两份（合计 148KB，占八份报告近三成），但它们恰恰是**最不该抄**的部分；真正的增量全在产出层与感知层。**第一版文档的权重分配（K/Q/A/C 四层）是对的，但"为什么"要换成"成熟度倒挂"这个说法。**

## 2. 五处分歧与裁决

判定原则：**源码实读 > 单份报告推断；能跑的一手验证 > 文档描述。**

### X1 双轨写盘：收编，还是承认？（最核心）

| 方 | 主张 | 证据 |
|---|---|---|
| s2 | 模型无法直接改 docx/pptx/xlsx（46 个内置工具里没有 office 工具） | `internal/gaea/tool/builtin/` 全量 |
| s5 G1 | 模型**可以**改——经 `bash` 调 `.gaea/skills` 的 Python 技能；Go 原生编辑器只服务 UI | `bindings_office.go:79/123/215` |
| s7 | docx-js 管线若要进 Go 主干是 L 成本，**建议继续压在 bash+node 临时路径** | s7 §8.2 |
| 第一版文档 | "任何新工具都必须走 Go 原生 op，否则加深双轨" | 主文档 §8 风险表 |

**裁决**：三方各对一半，合成一条更准确的话——**"写"可以留在 Python，但"事实"必须回到 Go。**

- 生成类工作（从零排版一份 30 页报告）保留 Python 路径：Go 侧没有 docx 生成库，`gooxml` 只够 Title/Heading/段落（s7 §7），硬搬是 L 成本且开出第三条写盘路径。
- 但**每一次落盘都必须留下 Go 侧可读的事实**：路径、哈希、来源轮次、操作范围、能回滚的基线。现在 `RecordChange` 只覆盖 6 个工具，`bash` 被白名单排除（`internal/gaea/evidence/evidence.go:381-404`），所以 Python 写出来的文件对证据链、回滚、产物登记都是隐形的。
- 因此优先级要改：**"把 bash 写盘纳入事实链"（原 C1 的前置）应当排在"docx 机检"之前**——机检的对象如果是幽灵文件，检出来也落不进交付物台账。

> 这条裁决把第一版 P0 的顺序改了：不再是"K2→K3→Q1→A1"，而是"事实链 → K2/K3 → Q1 → A1"。

### X2 visual-judge：重复门禁，还是补位？

| 方 | 主张 | 证据 |
|---|---|---|
| s8 | visual-judge 与 `gaea_verify` 证据链重复，会造成双门禁，**不搬** | s8 §6.3 |
| s7 | 它补的是 gaea Verifier 缺的"绝对质量"维度（现有只是 0.02/0.20 的 before-after 像素 diff） | `gaea_verify.go:66-67` |
| s1 N8 | goal verifier 类"自动判定"在办公要慎用 | s1 §11 |

**裁决**：**协议要，插件形态不要，门禁必须三分。**

- gaea 的 `Verifier` 判的是"改前改后像不像"（回归），judge 判"目标达成没有"（对话证据），visual-judge 判"这一页能不能交"（绝对质量）。三者对象不同，不构成重复。
- 但 s8 的担心是对的：如果三者都往对话里抛结论，用户会看到互相矛盾的三句话。所以 Q5（验收分工）不是文档工作，是**产品规则**，必须写进交付卡：机检失败 → 阻断；judge fail → 阻断；diff 变化 → 仅提示。
- 另有一个 gaea 独有的事实：**子代理的视觉工具链已经存在**。`vision` 工具收 `image_path`（`tool/builtin/vision.go:28`），`docmd.RenderPDFPages` 能把 PDF 逐页出图（`internal/docmd/render.go:24`），所以 visual-judge 在 gaea 里可以就是一个 `RunAs: RunSubagent` + `AllowedTools: [bash, vision, read_file]` 的技能（`builtins.go:204-208` 的 format-convert 是现成样板）。
- **但被权限卡住**：`bash` 跑 `soffice`/`pdftoppm` 属写操作，默认 `mode=ask` 会弹卡（`internal/gaea/permission/permission.go:17-24` 的三态 + 写类 fallback），而审批是全局单槽串行（s5 G6）。让一个"只读评审员"每次评审弹两张卡，产品上不可接受。

**结论**：Q4 的真实前置不是"渲染能力"，而是**一个 ReadOnly 的 Go 渲染工具**（`doc_render(rel, pages) → png[]`，包一层 `docmd.RenderPDFPages`）。加了这个，visual-judge 才真的是 M 而不是"看起来 M、落地要动权限模型"。

### X3 上下文条：gaea 到底有没有？

| 方 | 主张 |
|---|---|
| s3 | "gaea 完全空白（ComposerToolbar 无 context/token 匹配，只有 ContextView 整页）" → 列为最值得抄第一名 |
| s6 | "上下文是主区 tab（`App.tsx:799`）+ 百分比 pill" |
| **实读** | `frontend/src/gaea/components/ContextModal.tsx:1-19` 文件头写着"蒸馏规划 2.5e …　ContextPill：codex 式「剩余上下文 %」常驻徽标"；`AppStatus.tsx:103-129` 有百分比、进度条、75%/90% 分色与"即将强制压缩"文案 |

**裁决**：**s3 读旧了，此项从"最值得抄"降为"已存在，只差分项构成"。**

gaea 已有：常驻徽标、百分比、75%/90% 分色、压缩水位提示、`ContextModal`（含"距压缩 ≈N tokens"），以及 `ContextView.tsx` 里的**六分类构成 + 图例 hover 联动**（`ContextView.tsx:1-28,58-64`）。所以真实缺口只剩"把构成压进 composer 徽标的 hover 面板"，**S 成本，且不该占 P0**。

> 这一条是本次交叉校验最值钱的发现：子代理读的是仓库代码，但"空白"判断依赖它对 UI 的抽样，而 gaea 的上下文面板恰好分散在 `ContextModal`/`ContextView`/`AppStatus` 三处。**任何"gaea 空白"的结论，落地前必须再 grep 一次。**

### X4 技能分层：抄它，还是修自己？

| 方 | 主张 |
|---|---|
| s7 | ZCode 的"渐进披露"是**假渐进**：合同场景冷启动仍要 46.5k tok，`design-system.md` 80KB 占 48% 且被无条件加载 |
| s4 | gaea 的索引压缩比 ZCode 平滑（更好），但 `references/*.md` 被一次性拼进正文（更差） |

**裁决**：**两侧同病，ZCode 不是解药，只是病历。**

源码确认 gaea 的问题：`internal/gaea/skill/skill.go:384-422` 的 `loadBodyWithReferences` 注释写得很坦诚——"so depth material is available without on-demand resolution"，即**故意**把 references 全量拼进正文，换取"不用二次解析"。ZCode 反过来：允许按需，但主 SKILL.md 强制要求加载最大的那份。

所以 K6 的正确表述不是"抄 ZCode 的分层"，而是"**修自己的二级加载，并把 ZCode 的 46.5k 当反例**"：索引给路由、正文只给当前 route、references 正文不进 L1 前缀缓存区（`boot/sysprompt.go` 目前把技能索引/事实/晨报都拼进稳定前缀，s4 报告已指出）。

### X5 自动续跑：不抄，还是已经有了？

| 方 | 主张 |
|---|---|
| s1 N8 | "goal verifier fail-open + 自动续跑"在办公要默认关闭 |
| **实读** | gaea 已经有两道自动续跑闸：`agent_run.go:334-339`（task gate → goal gate，命中即 `continue`）、`:343-358`（final readiness gate，带 `maxFinalReadinessBlocks` 与"停滞检测"） |

**裁决**：**"不抄"这一条对 gaea 无效——它早就有了，而且做得比 ZCode 保守**（有轮次上限、有停滞判定、`impossible` 分支）。

真正该问的不是"要不要抄"，而是"**现有的 judge 在办公场景会不会误判**"：judge 的证据来自 transcript（`judge.go:50-60` 只取最近 30 条消息），一份 30 页文档的"完成"很可能不在最近 30 条里。这是一个**应该单独立项的疑问**，而不是"不抄"。

> 推论：第一版文档 §6 的 N8 应改为"已存在，需评估证据窗口"，从"不采清单"移到"待验证清单"。

## 4. 依赖图：谁卡住谁

第一版把 20 条并列成三档，掩盖了四条隐藏依赖。画出来是这样（`→` 表示"后者依赖前者"）：

```
[事实链：bash 写盘入证据链] ──→ [Q1 docx 机检] ──→ [Q6 体检报告上卡]
        │                            │
        │                            └──→ [C1 投影版本]（机检要知道查的是哪一版）
        │
        └──→ [K1 场景工艺]（生成完要能判"合不合格"，否则场景手册只是安慰剂）

[ReadOnly 渲染工具 doc_render] ──→ [Q4 visual-judge] ──→ [Q5 三门分工]
                                        ↑
                              [权限：只读子代理不弹卡]

[K6 二级加载] ──→ [K1 场景工艺]（不分层就塞不进 7 本场景，会撞 L1 前缀）

[A1 锚点] ──→ [A2 视图回报] ──→ [A3 截图取证]
```

四条隐藏依赖，正好对应第一版四个被低估的项：

1. **Q1 依赖事实链**：否则机检对象不在台账里，"体检通过"和"交付物"对不上号。
2. **Q4 依赖只读渲染工具 + 权限**：这是 X2 的结论，成本从 M 修正为 M+（多一个工具 + 一次权限白名单设计）。
3. **K1 依赖 K6**：不分层直接搬 7 本场景，会把 L1 前缀撑爆（s4 已警告前缀失效风险）。
4. **A2 依赖 A1**：没有锚点，视图回报只能报"第 3 页附近"，价值减半。

## 5. 重排后的优先级

按"依赖在前 + 一次只动一层"重排：

### T0 · 地基（必须先做，2~3 人日）

| 项 | 内容 | 为什么必须先做 |
|---|---|---|
| **F1 事实链收编** | `bash` 写盘（含 Python 生成的 docx/xlsx/pptx）在落盘后登记：路径 + 哈希 + 轮次 + 可回滚基线；证据白名单加 bash 产物的显式登记通道 | 没有它，后面所有质检与验收都在给幽灵文件打分 |

## 7. 给决策者的三个选项

> 2026-10-24 更新：与 ZCode 的四+三轮对话后，三条待拍板已收敛为双方共同建议，见
> [`zcode-office-decision-memo-2026-10.md`](zcode-office-decision-memo-2026-10.md)。本节三个选项保留作为背景推导。

**选项 A：先地基（推荐）**
F1 + F2 约一周落地（实现 2~3 人日 + 回归验证），随后 T1 才站得住。代价是本轮"看不见产出"，收益是后面每一项都不用返工。
判据：Python 生成的 docx 能在「变更/证据」面板里被回滚；模型能对第 N 页截图。

**选项 B：先可见（快感优先）**
K2 + K3 + CJK 归一（3 人日，零依赖），先让"机检能挑出错"这件事被看到，再回头补地基。
