# 市场调研：AI 办公「大文件处理」，2026-08

> 目的：为 gaea 通用办公的「大文件」场景提供设计依据，承接前几轮调研（开工前、
> 编辑输出、交付 UX、记忆自进化）中反复出现的同一缺口——文件越来越大时，
> AI 怎么读、怎么注入、怎么不超界。本轮集中调研各头部产品与开源工程方案对
> 「大文件」的处理策略：体积/页数上限、超限提示、分块摘要、按需读取、流式 OCR。
> 来源为 2026 年公开资料与官方文档。

## 0. 一句话结论

2026 年行业共识不是「能传多大」，而是**怎么把大的东西变小进上下文**：
① 头部产品普遍把单文件上限抬到百 MB 级（ChatGPT 512MB / Claude 500MB / 千问 150MB），
但真正解决可用性的不是上限本身，而是**分块摘要（map-reduce）**与**按需读取**——
千问 500 页超长文、WPS 灵犀读完整本书、豆包分段摘要都是同一套路：大文件不进上下文，
进上下文的是它的**目录与摘要**，细节按页/按段再读。② PDF 类文件普遍有**页数上限
保护**（Gemini/千问 500-1000 页、MinerU 默认 1000 页），并支持**流式分页 OCR**。
③ 所有超限路径都要有**明确提示**（截断标记、页数提示、跳过提示），而不是静默发生。
gaea 现状是「防御性上限齐全但策略缺失」：64KB 硬截断、10MB 附件提示、5MB 搜索跳过、
OCR 无页数保护——缺的正是行业里已被验证的三件事：**分块摘要管线、@ 大文件按需读取、
PDF 页数上限与流式 OCR**。

## 1. 竞品矩阵：大文件方案

| 产品 | 体积/页数上限 | 超限策略 | 大文件读取方式 | 可蒸馏优点 |
|---|---|---|---|---|
| ChatGPT（2026） | 单文件 512MB；表格/CSV ≤50MB；图片 ≤20MB；文档总 200 万 token | >200 页建议拆分；官方建议逐个摘要、「摘要的摘要」 | 上传即上下文，表格与 PDF 可对话 | ① 单文件上限高；② 超长文档官方方案=逐文件摘要再合并 |
| Claude | 500MB/文件（free 30MB）；PDF ≤1000 页 | 大文档建议拆小段 | Files API 500MB；项目知识库预载 | ③ PDF 页数上限明确（1000 页） |
| Gemini | PDF ≤50MB 或 ≤1000 页 | 扫描 PDF 内部表示放大 token、易超界 | 多 PDF 单请求 ≤1000 页 | ④ 页数与体积双上限 + 明示扫描件代价 |
| Kimi | K2.6 单轮约 128K token；K3 1M token | 文件过大建议拆分多次发送 | 单文件进上下文，超出则分轮 | ⑤ 上下文窗口大但仍有明确超限指引 |
| 千问办公 | App 一次 10 文件、500 页超长文；file-extract API 150MB；Qwen-Long 1000 万 token | 超长文自动分段处理 | 摘要/分析一键到结果；API 侧长文管线 | ⑥ 500 页超长文可读；⑦ 长文 token 扩展兜底 |
| WPS 灵犀 | 实测可读完一整本书 | OCR 太大时智能**分页 OCR**；KAG 知识增强 | 文档先解析再按需引用 | ⑧ 分页 OCR 防整本扫描件卡死；⑨ 知识增强辅助 |
| M365 Copilot | 大文档摘要/引用指南 ≤150 万字或 300 页 | 超限时走摘要指南而非整读 | 按引用范围生成摘要 | ⑩ 明确「摘要指南」替代整读 |
| MinerU（开源） | max-convert-pages 默认 1000 | >50 页流式转换 + 分块缓存 | 流式 + 分块缓存 | ⑪ 流式 + 分块缓存工程范式 |
| Claude Code（工程侧） | 大文件不整读 | 先 grep 定位再按 offset 读相关段 | 关键词定位 + 按行/偏移读取 | ⑫ 大文件「定位再读」而非「截断塞入」 |
| 飞书 aily | 单文件 100M；在线 ≤200 页 | 表格大切片带表头拆多片 | 智能切片 | ⑬ 表格大切片按表头拆多片 |
| Cherry Studio（本地） | 知识库文件入库 | chunk 切块 → 本地向量化 | 检索相似片段进上下文 | ⑭ 本地 chunk + 向量检索 |
| 豆包 | 无公开硬上限 | 分段摘要突破长度限制 | 分段处理再汇总 | ⑮ 分段摘要的工程落地 |

## 2. 可蒸馏的优点清单（映射到 gaea）

1. **大文件分块摘要（map-reduce）**：千问 500 页超长文、WPS 读完整本书、豆包分段摘要、
   M365 摘要指南、ChatGPT「摘要的摘要」——同一模式：超过单轮上下文的文件先分块
   （按页/按字符）→ 逐块摘要 → 合并为结构化「文件摘要」（章节、要点、数据表清单），
   上下文里放的是摘要，细节按块再读。gaea 现在只有硬截断，没有这条管线。
2. **@ 大文件按需读取（而非截断丢弃）**：Claude Code 大文件先 grep 定位再按 offset
   读相关段、WPS 分页 OCR、aily 智能切片——超过注入上限的文件不是一刀切掉，而是
   「目录/摘要 + 按需分页/分段读取」。gaea 的 64KB 截断目前就是一刀切。
3. **PDF 页数上限 + 流式分页 OCR**：Gemini 1000 页/50MB、千问 500 页、MinerU 默认
   1000 页且 >50 页流式、WPS OCR 过大时智能分页——扫描件 OCR 必须按页流式 + 进度 +
   上限保护，否则整本扫描 PDF 一次转完会长时间阻塞且 token 爆炸（Gemini 明确警告
   扫描 PDF 内部表示放大）。gaea 的 OCR 管线无页数保护、无流式进度。
4. **超限路径的明确提示**：截断标记（xlsx 已有）、页数提示、搜索跳过提示——所有
   「没读全」的场景都要让用户看得见，而不是静默降级。gaea 的全文搜索 5MB 跳过 /
   20 万字符截断目前完全静默。
5. **超大预览懒加载与截断标记**：MinerU 流式、千问在线 ≤200 页、aily 在线 ≤200 页——
   大文件预览分页加载，明确标「已截断，共 N 页」。gaea 的 xlsx 已有 Truncated 标记，
   docx/pdf/md 预览是整读转换、无标记。
6. **多文件「摘要的摘要」**：ChatGPT 官方建议超长文档逐个摘要后汇总——一次引用多个
   大文件时，先逐文件摘要，再合并成总览，而不是把 N 个文件都塞进上下文。
7. **资料卡片大文件标注**：千问/aily 上传即标注大小与页数——gaea 资料面板没有大小/
   页数信息，用户无法预判「这个大文件 AI 能不能读完」。

## 3. gaea 现状盘点（基于代码，2026-08-10）

### 已具备
- **上下文兜底**：百万 token 窗口 + 压缩（verbatim 尾部预算 TailTokens=16384，
  `internal/gaea/agent/compact.go:38`）——大文件有整体兜底，但单文件仍受注入上限约束。
- **@ 引用按需注入 + 上限标记**：`maxFileRefBytes=64KB`
  （`internal/gaea/control/refs.go:20`），超限截断并带 `[truncated; file is N bytes]`
  标记（`refs.go:253-254`）——有防御，但 64KB 之后的内容没有替代读取路径。
- **附件体积控制**：图片 ≤10MB（`internal/gaea/control/attachments.go:19`）；前端对
  >10MB 非图片文件仅 confirm 提示（`frontend/src/gaea/components/Composer.tsx`）。
- **xlsx 预览截断标记**：超大表格截断并置 `Truncated` 标记
  （`internal/office/xlsxpreview/xlsxpreview.go:141/145`）——表格方向的标杆已在。
- **docx/xls/pdf 转 Markdown**：预览经 `docmd.Convert`（`internal/app/gaea_preview.go`），
  PDF 支持 `pages` 参数（"1-5"/"1,3,5"，`docmd.go:30-35`）并有 OCR 扫描件回退
  （`docmd.go:536-537`）——但没有截断标记、没有页数上限。
- **全文搜索防御**：原始文本 >5MB 不索引、单文档 ≥20 万字符截断
  （`internal/gaea/wssearch/wssearch.go:60-61`）——有防御但静默。
- **固定资料注入预算**：单文件正文 ≤1600 字符、整块 ≤8000
  （`internal/gaea/pins/pins.go:21-22`）。

### 缺失（本轮差距）
- **无大文件分块摘要管线**：docx/pdf 预览直接整读转换，超大 PDF 一次转完，无页数
  上限保护，无「摘要后引用」入口。
- **@ 超限后无替代读取路径**：64KB 是硬切，没有「注入目录/摘要 + 按需分页读取」的
  智能策略（对标 Claude Code grep+offset、WPS 分页 OCR）。
- **扫描件 OCR 无上限与流式**：整本扫描 PDF 回退 OCR 时逐页串行识别，无页数保护、
  无进度、无取消，超大扫描件可能长时间卡住（对标 WPS 分页 OCR / MinerU 流式）。
- **静默降级**：全文搜索 5MB 跳过/20 万字符截断无提示；md/文本预览整文件读
  （`os.ReadFile`，`gaea_preview.go:116/129`），超大文件无截断标记。
- **资料面板无大文件标注**：大小/页数信息缺失，无法预判读取代价。

## 5. 设计决策与强化清单（映射 gaea）

### P0 大文件可用性核心（先做）
1. **大文件分块摘要管线（map-reduce）**：对超过阈值（如 >300 页或 >2MB 的
   docx/pdf/txt/md）的文件，先按页或按 ~2 万字符分块 → 逐块摘要（可复用现有
   provider，串行或分批）→ 合并成结构化「文件摘要」（总页数、章节清单、要点、
   数据表清单、结论），摘要入上下文，原始文件保留、需要细节时按块再读。落点：
   新增 `summarizeLargeFile` 服务 + @ 与预览两处入口；对标千问 500 页超长文、
   WPS 整本书、豆包分段摘要、M365 摘要指南。
2. **@ 大文件智能策略**：@ 引用 >64KB 时不再硬截断，改为三选：① 注入「目录 + 摘要」
   （先走分块摘要）；② 按需分页/分段读取（提示模型用 pages/offset 读指定区间，
   对标 Claude Code grep+offset）；③ 明确告知用户「文件过大，已注入前 N KB +
   目录，可要求按章节深入」。落点：复用 `refs.go` 注入点，新增大文件分支；
   对标 WPS 分页 OCR、aily 智能切片。
3. **PDF 页数上限 + 流式分页 OCR**：预览/转换默认页数上限（建议 300-500 页，
   对标千问 500 页、MinerU 默认 1000），超限提示「建议拆分或按页读取」；扫描件
   OCR 改为按页流式，回传进度（x/N 页）+ 可取消，避免整本扫描件长时间阻塞。
   落点：`docmd.Convert` 增加页数守卫与进度回调；对标 Gemini 的扫描件放大警告、
   WPS 分页 OCR、MinerU 流式。

### P1 深化
4. **搜索大文件提示与分块索引**：全文搜索跳过 >5MB / 截断 >20 万字符时在结果中标注
   「该文件过大未完整索引」；按需对超大文件分块索引（文档按页、表格按 chunk，
   对标 Cherry Studio 本地向量库 / aily 切片）。
5. **超大预览懒加载 + 截断标记**：docx/pdf/md 预览超限时带「已截断，共 N 页 /
   共 X MB」标记 + 分页加载（对标 xlsx 既有 Truncated、MinerU 流式）。
6. **多文件「摘要的摘要」**：一次性引用多个大文件时先逐文件摘要，再合并为总览
   （对标 ChatGPT 官方建议）。
7. **资料卡片大文件标注**：MaterialsPanel 显示文件大小 + 页数预估（PDF 可读页数），
   并提供「摘要后引用」按钮（对标千问/aily 上传即标注）。

### 明确不做
- 把单文件体积上限放宽到云端级（ChatGPT 512MB / Claude 500MB）——本地工具定位，
  保持合理上限，靠策略（摘要 + 按需读取）解决可用性，而不是靠无限放宽。
- 云端存储/上传下载、跨设备大文件同步（本地优先）。
- 把大文件全量塞进上下文（坚持摘要 + 按需读取，与「@ 按需加载」纪律一致）。

## 6. 落地优先级建议

- **本轮优先（P0）**：① 大文件分块摘要管线（map-reduce：分块 → 并行摘要 → 合并）；
  ② @ 大文件智能策略（>64KB 注入目录+摘要、按需分页/分段读取）；
  ③ PDF 页数上限 + 流式分页 OCR（300-500 页守卫 + 进度回传）。
- **其次（P1）**：全文搜索大文件提示与分块索引；超大预览懒加载 + 截断标记；
  多文件「摘要的摘要」；资料卡片大文件标注。
- **明确不做**：无限放宽体积上限、云存储、全量塞入上下文。

## 7. 结论

行业对大文件的答案已经从「能传多大」转移到「怎么把大的变小」：分块摘要、按需读取、
页数保护、明确提示，四条路头部产品高度一致。gaea 现状是防御性上限齐全（64KB /
10MB / 5MB / 1600 字符 / 16384 tail），但缺的是策略层——硬截断没有替代读取路径、
预览整读没有截断标记、搜索静默跳过、OCR 无页数保护。三个 P0 都复用现有
docmd/refs/wssearch/固定资料基建，本地完成、零外部依赖：做完后大文件从「能用」
升级为「好用」——大文件进 gaea 不再是一刀切截断，而是「先有目录和摘要，细节
按需再读」，正好承接开工前（@ 按需加载）与记忆（自动做梦）两轮的上下文纪律。
