## 2. 九个对照域

### 域 A：Agent 循环与回合生命周期

**Codex 实现要点**

- `session/turn.rs::run_turn`：预采样压缩（`run_pre_sampling_compact`）→ MCP 依赖解析 →
  捕获 step context（一次采样请求内的工具/上下文/世界状态同源）→ 技能注入 → 循环内：
  采样 → 工具跟随 → 回合中自动压缩（`run_auto_compact`，`CompactionReason::ContextLimit`，
  `CompactionPhase::MidTurn`，压缩后以 `InitialContextInjection::BeforeLastUserMessage`
  把世界状态重注入到最后一条用户消息前）→ 轮转（`should_roll_over`）→ 停止 hooks。
- `codex_thread.rs`：回合是**一等对象**——`start_or_steer_turn`（空闲即开新回合，运行中
  则并入当前回合）、`start_turn_if_idle`、`recover_turn_if_idle`（**保留原 turn id 恢复
  被打断的回合**）、`steer_turn`（带 expected_turn_id 的中途转向，防止旧 UI 误转向）、
  `suspend_turn_and_shutdown`（挂起并迁移，拒绝非 root 线程挂起）。
- `session/input_queue.rs`：运行中提交的用户输入先进队列，采样间隙 drain，作为当前回合的
  后续输入（mailbox 投递语义），不是丢弃也不是另开回合。
- `turn_metadata.rs` / `turn_timing.rs`：每个回合记录 model、reasoning_effort、
  user_input_requested_during_turn、workspace git 元数据（remote/commit/dirty）、窗口与
  分段时间。
- `elicitation.rs`：提问/审批等「elicitation」注册计数，全部结束前暂停工具结果回传。

**gaea 现状**

- `agent_run.go::runDirect`：steer 队列（`consumeSteer` 每步消费）→ stream → 流恢复
  （最多 3 次，保留部分输出注入恢复提示）→ length 截断 nudge → 空终态重试（3 次）→
  usage/预算闸门 → `maybeCompact` → 工具批执行 → task 闸门 / goal 闸门 / final-readiness
  闸门 → 重复检测 / 参数风暴断路器 / bg start-kill 检测 → maxSteps 的 grace round。

**优劣对照**

- gaea 的 task/goal/final-readiness 三闸门 + 流恢复 + 空终态重试是办公向的、Codex 没有
  的成熟机制；Codex 的回合语义更强在**工程化**：恢复保留 turn id、挂起迁移、带 turn id
  的中途转向、输入队列 mailbox。
- gaea 明确注释「no mid-turn compaction — cache grows monotonically within each turn」；
  Codex 有 pre-turn + mid-turn 两级压缩（见域 B）。

**可蒸馏**：中回合压缩（P1，见 C8）；恢复/转向语义（P2，见 C10）。

### 域 B：压缩与上下文窗口

**Codex 实现要点**

- `session/context_window.rs`：`AutoCompactTokenLimitScope::Total` 与
  `BodyAfterPrefix` 两种口径——后者只把 **cached 前缀之后新增的 token** 计入压缩阈值，
  命中缓存的长前缀不再逼迫压缩；完整窗口是硬顶；`token_budget` 的 fallback buffer 只在
  有回退提示可用时才预留。
- `turn.rs`：pre-turn 压缩（`run_pre_sampling_compact` 在记录用户消息前触发，
  注释明确「TODO：预估 pending items 提前压缩」）、mid-turn 压缩（采样后
  `token_limit_reached` 即 `run_auto_compact` + 轮转）、**模型切换压缩**
  （`maybe_run_previous_model_inline_compact`：comp_hash 变化或切到更小窗口模型时，
  用上一模型上下文压缩后交给新模型，还带 fallback step context 重试）。
- `compact_remote_v2.rs`：远端压缩 v2（图片预算、多尝试）。

**gaea 现状**

- `compact.go`：三档——soft 50% notice → prune 陈旧工具结果（`PruneStaleToolResults`，
  KeepErrors/KeepProtected 保错误与基础上下文，先存档）→ LLM 摘要
  （`<compaction-summary>` 不可变 digest，前缀保缓存）→ mechanical fold 兜底；
  ForceRatio 90%、TailTokens 16384、pinned first user turn 上限。

**优劣对照**

- gaea 的「不可变 digest 前缀保缓存 + KeepErrors + 存档」设计扎实，与 Codex 的 cache-first
  思路等价，甚至更细（Codex 没有 KeepErrors/KeepProtected 的等价物）。
- gaea 缺：**中回合压缩**（长工具链回合窗口会单调涨满）；**BodyAfterPrefix 口径**
  （办公长会话开头往往有大量固定资料，cached 前缀不应计入压缩阈值）；**模型切换自动压缩**
  （切换 provider/model 时旧上下文直接带过去，无 comp_hash 感知）。

**可蒸馏**：C8 中回合压缩；C11 BodyAfterPrefix 口径 + 模型切换压缩（P2）。

### 域 C：工具执行与审批策略

**Codex 实现要点**

- `exec_policy.rs`：`AskForApproval` 四态——Never / OnRequest / UnlessTrusted /
  Granular（规则审批与沙箱审批可分别开关）；未匹配命令由「危险命令启发式 + 沙箱能力」
  推导决策（危险或裸奔 → Prompt，Never 下 → Forbidden）；`prompt_is_rejected_by_policy`
  区分规则 prompt 与沙箱/升级 prompt；规则文件分层（用户/项目/requirements），审批通过
  时**回写策略修订**（`append_amendment_and_update`）。
- `session/mod.rs`：`request_command_approval` / `request_patch_approval` /
  `request_permissions_for_environment`（环境级权限升级）/ `request_user_input`——
  全部先注册 pending approval（oneshot 挂回 turn state），再发事件，再阻塞等
  `ReviewDecision`。
- `protocol.rs`：`ReviewDecision` = Approved / ApprovedExecpolicyAmendment /
  ApprovedForSession / ApprovedMcpPolicyAmendment / NetworkPolicyAmendment /
  **Denied{rejection}（拒绝但会话继续）** / TimedOut / **Abort（拒绝并终止本轮）**。

**gaea 现状**

- `permission.go`：`Policy{Mode(默认 ask), Allow/Ask/Deny 规则 + subject glob}`，
  只读工具恒 Allow，优先级 deny > ask > allow > 兜底——纯函数、可测。
- `controller_approval.go`：hardAskTools（cost_save/remember/forget/knowledge_add 等
  持久化写入**任何权限级别都强制逐条确认**）、auto/yolo 等级、会话放行 granted map、
  串行化 prompt、`Notification` hook 在等待审批时发通知。审批回复只有
  `{allow, session}` 两字段。

**优劣对照**

- gaea 的 hardAskTools 比 Codex 更安全（Codex 靠 permission profile，无「任何级别都
  强制确认」的硬清单）；gaea 的策略是纯函数，测试成本低。
- gaea 缺：Denied(rejection) 与 Abort 的语义区分（现在是「拒绝=放行 false，工具报
  approval aborted」，无「继续尝试别的」与「终止本轮」之分）；TimedOut；「Never 下
  Prompt 直接拒绝」的无人值守语义；权限升级请求（临时放开某目录/某工具，而不是改全局
  级别）；审批通过时把规则写回策略文件（现在是内存 granted map，重启即失）。

**可蒸馏**：C4 审批决策语义 + 权限升级 + 策略文件化（P1/P2）。

### 域 D：记忆管线

**Codex 实现要点**

- `memories/write/src/phase1.rs`：启动认领（年龄窗/空闲时长/限额/互斥）→ 并行抽取
  （并发上限）→ 严格 schema（`raw_memory` / `rollout_summary` / `rollout_slug`，
  `deny_unknown_fields`）→ 脱敏（`redact_secrets`）→ 保留期裁剪。
- `phase2.rs`：**全局锁 + 租约**（`JOB_LEASE_SECONDS`）→ **git baseline 工作区** →
  同步输入后跑 `memory_workspace_diff`，**无变化且产物有效就 no-op 成功**（省一次
  LLM 调用）→ 有变化才写 diff 文件、spawn 一个**沙箱化、锁死配置的 consolidation
  agent**。
- 产物分层：`memory_summary.md`（常载，token 截断）→ `MEMORY.md`（可 grep 注册表）→
  `rollout_summaries/`（按需打开）+ `skills/`。
- 读路径：`read_path.md`（决策边界、4-6 步检索预算、`<oai-mem-citation>`
  citation_entries + rollout_ids、陈旧提示、仅显式要求才更新）+ `citations.rs`
  （程序化解析）+ `usage.rs`（按记忆路径分类遥测）。

**gaea 现状**

- `memory/recall.go`：画像注入 600 rune + 逐轮 RecallBlock 800 rune 预算；关键词/时间/
  高频/规则（procedural +0.5）打分——**主动注入**。
- `memory/promote.go`：`remember(session=true)` 两阶段 + `promote_session_facts` 提升为
  永久记忆；`dream.go` / whisper 管线做事实抽取/合并/审计；MemoryHub 统一检索
  （GaeaUnifiedSearch）。

**优劣对照**

- gaea 的主动注入（有预算的每轮 recall）比 Codex 的「模型决定是否检索」更适合办公高频
  小记忆；Codex 的文件分层（summary 常载 + registry grep + rollout 按需）比 gaea 的
  平铺事实库更适合**长程一致性**。
- gaea 完全缺：**引用可追溯**（回答用了哪条记忆、可点击溯源、陈旧提示）——这是
  办公用户验证「你引用的资料是不是真的」的信任闭环。
- Codex 的 git baseline no-op 优化值得借鉴（省 token）；gaea 的 dream 每次都会跑合并。

**可蒸馏**：C2 引用可追溯（P1）；C3 渐进披露分层 + no-op 优化（P2）。

### 域 E：上下文碎片架构

**Codex 实现要点**

- `context/mod.rs`：40+ 个 `ContextualUserFragment`（BaseInstructions、CurrentTimeReminder、
  PermissionsInstructions、TokenBudgetContext、CompactionSummary、ModelSwitchInstructions、
  RolloutBudgetContext…），每个都有 `role` / `content_kind`（稳定分类）/
  `markers`（起止标签，用于事后识别注入内容）/ `requires_separate_message`。
- `world_state`：上下文按**节**做快照与 diff，只有变化节才重注入
  （`render_diff`），例如 `context_window` 节只在 agent path 变化时重发。
- `token_budget_context.rs`：以 `<context_window>` 标签把 first/current/previous window
  id 注入 developer 角色，模型知道自己处于哪个上下文窗口。

**gaea 现状**

- `contextview`：六分类 token 构成（User/System/…）+ 事件（inject/compact/prune/switch/
  mode）+ 趋势图 + usage 锚定——**统计侧望远镜**，但注入侧没有统一抽象：`store.ts`
  / `agent_run.go` 各自拼 prompt 片段，无 markers/content_kind，无法识别与裁剪。

**优劣对照**

- gaea 的 ContextView 是「看到什么」，Codex 的 fragments 是「注入管线」；把两者接起来
  才能回答「哪些注入可裁剪、预算被谁吃掉」。
- Codex 的按节 diff 注入（世界状态变化才重注入）对 gaea 的「常用资料固定 + 项目说明
  整段注入」是直接改进。

**可蒸馏**：C7 注入碎片类型化 + 按节 diff（P2/P3）。

### 域 F：事件与可观测

**Codex 实现要点**

- `protocol.rs::EventMsg`：约 70 个变体——回合（TurnStarted/Complete/Aborted）、
  用量（TokenCount）、消息（AgentMessage/Reasoning/Delta）、工具细粒度
  （ExecCommandBegin/OutputDelta/End、McpToolCallBegin/End、WebSearchBegin/End、
  ImageGenerationBegin/End、PatchApplyBegin/Updated/End）、审批
  （ExecApprovalRequest/ApplyPatchApprovalRequest/RequestPermissions/RequestUserInput）、
  上下文（ContextCompacted/TurnDiff/PlanUpdate）、生命周期（ItemStarted/Completed、
  HookStarted/Completed、EnteredReviewMode）、子代理（SubAgentActivity、Collab*）。

**gaea 现状**

- `event/event.go`：19 种（TurnStarted/Reasoning/Text/Message/ToolDispatch/ToolResult/
  Usage/Notice/Phase/ApprovalRequest/AskRequest/TurnDone/CompactionStarted/Done/
  RequestHeader/Retrying/Steer）；`trajectory` 投影为扁平事件账本（header/tool/compact/
  ask/approval + parentId 嵌套 + 检查器/搜索/统计）；`contextview` 投影为六分类时间线；
  事件日志 append-only + 黄金测试（日志即真相，可回放）。

**优劣对照**

- gaea 的「事件 → 投影 → 回放」架构优于 Codex 的直发（Codex 无黄金测试回放）；但 gaea
  缺工具的 **Begin/OutputDelta/End 细粒度事件**（TaskCenter 目前 2s 轮询
  `GaeaTaskOutput` 补实时输出）、缺 **PlanUpdate 流式计划事件**（目标/待办卡是回合结束
  回填而非实时推进）、缺 **HookStarted/Completed** 生命周期事件。

**可蒸馏**：C9 工具级事件 + PlanUpdate（P1/P2）。

### 域 G：协作模式与计划流

**Codex 实现要点**

- `collaboration-mode-templates/templates/plan.md`：三阶段契约（环境探索 → 意图问答 →
  实现问答）、模式纪律（持续到显式结束、用户命令不越权、禁止变异动作、先探索再提问）、
  决策完备的 `<proposed_plan>` 块。
- `config_types.rs`：`ModeKind` 仅 Plan/Default 两档，`allows_request_user_input`
  （Plan 才允许提问工具）；`tui/src/collaboration_modes.rs`：preset 过滤 + 轮换。
- `turn.rs`：`PlanModeStreamState` / `ProposedPlanItemState` / `handle_plan_segments`——
  计划在流式生成时就被结构化拆分并作为独立 item 发射（`PlanUpdate` 事件）。

**gaea 现状**

- `agent_plan.go` + `controller_plan.go`：单轮生成严格 JSON 开工计划（goal/steps/
  resources/tools/questions）→ AskCard「确认执行/先调整」→ plan-mode gate 在批准前
  block 写工具（ask 仍可用）；`AutoPlan` off/ask/on 配置。

**优劣对照**

- gaea 的开工计划卡（结构化 + 硬门）在办公场景比 Codex 的对话式规划更直接；缺的是
  **模式作为会话状态**（切换器）、「决策完备」要求、探索先行纪律、以及**计划流式
  结构化**（现在是回合结束一次性拿 JSON）。

**可蒸馏**：C1 会话模式切换 + 计划流式事件（P1）。

### 域 I：AGENTS.md / 技能 / 项目约定

**Codex 实现要点**

- `agents_md.rs`：项目根标记向上探测（默认 `.git`）→ root→cwd 逐层收集并连接
  （`AGENTS_MD_SEPARATOR`）→ `AGENTS.override.md` 本地覆盖 → `project_doc_max_bytes`
  字节预算 → untrusted 项目跳过 → 并发祖先探测上限 256。

## 4. 新增候选详细说明

### C8 中回合压缩（P1 / M）

这是本版最重要的发现。gaea 在 `agent_run.go` 明确注释「no mid-turn compaction — cache
grows monotonically within each turn」——一次办公长任务（批量文档、整表清洗、多轮
检索）的回合内，上下文只增不减，可能在中途就撞满窗口，而压缩要等回合结束才发生。
Codex 的做法：采样结束后查 `context_window_token_status`，`token_limit_reached` 即
`run_auto_compact(…, CompactionReason::ContextLimit, CompactionPhase::MidTurn)`，压缩后
以 `InitialContextInjection::BeforeLastUserMessage` 把世界状态（工作区/上下文快照）
重注入到最后一条用户消息之前，然后 `continue` 同一回合；若模型还要跟工具且有新窗口
请求则 `should_roll_over`。落地要点：gaea 已有 `maybeCompact`（摘要 digest + 前缀保
缓存），把调用点从「采样后、写 assistant 消息前」扩展为「工具批执行后、下一轮采样前
也检查一次」，并保证压缩后重注入的「基础上下文」与 `contextview` 的 usage 锚定一致。

### C9 工具级事件（P1/P2 / M）

Codex 对每类工具都有 Begin/OutputDelta/End 生命周期事件（ExecCommand、
McpToolCall、WebSearch、ImageGeneration、PatchApply），前端能实时渲染「正在做什么 +
输出流」。gaea 目前靠 `GaeaTaskOutput` 2s 轮询 + 尾随滚动补实时输出（v3.2.0），事件
流里只有 ToolDispatch/ToolResult 两态。蒸馏方案：给长任务工具（docx/xlsx 批处理、
检索、下载）发 ToolProgress/OutputDelta 事件，TaskCenter 订阅事件即推，轮询只做兜底
（对齐 Codex「事件为主、轮询兜底」）。同时补 `PlanUpdate` 事件：开工计划/目标卡随
回合内 `update_plan` 工具实时推进（Codex 的 `PlanUpdate(UpdatePlanArgs)`），而不是
回合结束回填。

### C4 审批决策语义（P1 / M，v1 的 C4 修订）

gaea 审批回复只有 `{allow, session}`，`controller_approval.go` 里拒绝即
「approval aborted」。Codex 的 `ReviewDecision` 把「拒绝」拆成三种：
`Denied{rejection}`（拒绝这条，模型继续想别的办法）、`Abort`（拒绝并终止本轮）、
`TimedOut`（无人值守自动判定）。这对办公「受控自主」直接有用：夜间批量任务里某一步
需要审批 → 无人响应 → 不是卡死也不是静默放行，而是挂起/超时并记录，醒来统一审。
配套两点：**权限升级请求**（Codex `request_permissions_for_environment`：模型请求临时
放开某目录/某工具，而不是改全局级别）；**策略文件化**（审批时「记住此规则」→ 回写
策略文件，重启不丢；gaea 现在是内存 granted map）。

### C11 BodyAfterPrefix + 模型切换压缩（P2 / M）

办公会话开头常有大量固定资料（常用资料固定 + 项目说明），这些是 cached 前缀。Codex
的 `BodyAfterPrefix` 口径让缓存前缀不计入压缩阈值，只有新增部分逼近阈值才压缩——
能显著减少办公长会话的无效压缩。模型切换时 Codex 用 comp_hash 感知并触发
previous-model inline compact（把旧模型会话压成摘要再交给新模型）。gaea 切模型是
直接把消息数组带过去，建议加「压缩后再切」的确认。
