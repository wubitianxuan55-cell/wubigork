# 造价数据库系统审视与完整规划（2026-10-07）

> 背景：工料法重塑（v4.457~463）已落地三层骨架，但用户指出「没有系统整理，都是看到一点说一点」。本文档是对**整个造价数据库**（数据层/Go 包/前端模块/真实库数据/绑定面）的全面审视结论与分期规划。后续刀路以本文为准，逐期关账。

---

## 一、系统现状（审视结论）

### 1.1 数据架构：三套价格数据并存，互不相通（根本问题）

| 数据集 | 表 | 规模（真实库） | 写入方 | 读取方 |
|---|---|---|---|---|
| 资料条目（价格手册） | cost_entries + components | 1590 条 / **组成行 0** | CostSave/ImportApply/ComposeApply/EstimateSediment/**PriceFetchApply**/tool cost_save | 检索/组价/比价/pricefeed 匹配/seed 输入/图谱/语义索引 |
| 工料机资源 | gf_resources + prices | 1486 条 / 调价历史 **0** | ResourceSave/SetPrice/SeedApply/ProjectApply | workcost 核算全链 |
| 询价库 | cost_inquiry_records | **0** 条 | InquirySave/ImportApply(OCR) | 询价面板/调差建议 |

**断点**：信息价发布（PriceFetchApply）只写资料条目；资源调价（SetPrice）只推进资源库；询价调差只写资料条目。**「一种材料一个当前价」不存在单一真相**——页面文案「信息价喂资源现行价」目前是愿景不是事实。

### 1.2 三代系统叠层，两代已死但未清理

| 代际 | 载体 | 现状 |
|---|---|---|
| 第一代：AI 组价（v4.2） | cost_entries + ComposeModal | **整链悬空**：ComposeModal 无挂载点、CostComposeApply 零调用、留痕 0 |
| 第二代：测算项目/五算（v4.150） | cost_projects/estimate_items/stage_values | UI 已退役；写路径全死；表数据 0（stage 4 条旧数据）；**V27 给退役表加的 19 列无任何读写路径（白做）** |
| 第三代：工料法（v4.457+） | gf_* 六表 | 活跃主链：资源 1486/定额 115/清单 115 条 4 案例/费率已落 |

### 1.3 绑定面与死代码（660 个绑定中约 20 个零 UI 消费）

- 五算 4 + 归因 1 + 复盘笔记 4 + 旧测算项目 8 + CostList 1 = **18 个纯死绑定**
- 工料法零消费：WorkcostProjectFees / Recompose / ResourceGet / BillItemSave / BillItemDelete = 5 个
- 有数据无界面：调价历史（绑定+PriceHistoryInline 组件都在，但零渲染）
- coststage/costinquiry 包内 DDL 与 SchemaV15 双路径并存（漂移风险）
- costproject 的 V27 新列（费率/工料机列）Go 侧 SQL 未接——表结构与代码脱节

### 1.4 价格源从未实战验证

2 个订阅源（重庆/四川造价信息网）已配置、enabled=1，但 **price_fetch 0 条**——抓取 cron 在跑但从未成功产出，或从未手动触发过。整条「信息价→确认→入库」链路未经验证。

### 1.5 真实库数据质量

- 零价资源 1 条；未被定额引用的资源 1529 条（正常——资源库是价格主数据，非全部被引用）
- 定额 115 条来自 4 个案例；组价留痕 0；询价 0；复盘笔记 0
- cost_entries 组成行 0 → 含量对标（contentband）、AI 组价的人材机拆解从未真正发生

### 1.6 用户心智模型（规划的对齐基准）

> 「造价数据库只是一个数据库：录入费率、清单、测算模版，但不是把它们加起来」
> 「清单是所有项目累计的清单列表」｜「项目文件导入在造价参考」（对标案例）｜「该删除就删除」

计算（加总/取费/合价）归导出的五表活公式 Excel；库=存取+检索+对标。

## 二、完整规划（四期，每期独立可验收）

### 一期：数据整合——建立「价格单一真相」（最高优先）

**目标**：一种材料一个价。三库从平行变为有向联动：信息价/询价 →（确认后）→ 资源现行价。

| # | 刀 | 内容 | 验收 |
|---|---|---|---|
| 1.1 | 价格源实战验证 | 手动触发重庆/四川两源抓取，修通解析/匹配问题；确认链路走通 | price_fetch ≥1 条成功记录，发布候选可确认入库 |
| 1.2 | 信息价→资源联动 | PriceFetchApply 确认发布时，按（名称归一+单位）匹配 gf_resources；命中项提供「同步推进资源现行价」勾选（默认开），写入调价历史（来源=信息价期数） | 发布一条信息价后，对应资源现行价更新且历史有记录 |
| 1.3 | 询价→资源联动 | 询价调差建议「更新成本库」同步提供资源价更新选项 | 同上 |
| 1.4 | 调价历史 UI | 资源库行内展开 PriceHistoryInline（死代码复活，绑定已在） | 每条资源可见历次调价（价格/期数/来源） |
| 1.5 | 价格来源显形 | 资源行标注价格来源（信息价/手动/导入/案例） | 用户能回答「这个价从哪来的」 |

不合并三张表（迁移风险大、语义确实不同：手册价/核算资源价/询价点），用**联动+来源标记**建立真相链。

## 三、排序理由与不做清单

**排序**：一期（价格真相）→ 二期（诚实清理）→ 三期（能力）→ 四期（运维）。一期最先因为它解决架构级断点（三库价格漂移），且价格源链路从未验证——在没验证的地基上继续堆能力是浪费。

**不做清单**（延续既有边界）：不做算量引擎、不做企业定额库、不做外部行业含量数据源、不在库内做加总计算（归 Excel 活公式）、不合并三张价格表、不迁移退役表（冻结声明即可）。
