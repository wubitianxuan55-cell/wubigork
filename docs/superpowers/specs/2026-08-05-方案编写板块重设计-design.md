# gaea「方案编写」板块重设计 — 投标方案智能体工作台（Bid Workbench）

> 日期：2026-08-05 ｜ 状态：待批准 ｜ 方向：方案 A（全流程投标方案工作台）
> 依据：代码审计（internal/office、internal/gaea、frontend OfficePage）+ 同类产品调研（BidMaster-Pro、广联达云清标 AI 编标、Loopio/Responsive、易标/智标星）

## 1. 目标与范围

将「方案编写」从通用章节文档编辑器重构为**投标技术方案智能体工作台**：以「招标解读 → 投标生成 → 投标检查 → 文档排版」四阶段流水线为核心，从底层数据模型开始重建，复用 gaea 现有 agent/工具/技能/知识库基础设施。

**现阶段范围：聚焦技术方案（技术标）编写**，即土壤修复类投标技术方案的长篇结构化编写与交付。图纸解析、清单解析、成本测算/商务报价、演示 PPT 等能力由 gaea 其他板块后续迭代，本设计仅预留接口、不纳入实现。

范围：
- 后端 `internal/office/proposal` 全量重构（数据模型、解析、生成、校验、导出、流水线、迁移）。
- 前端 `OfficePage` 重构为三栏工作台 + 流程步骤条，视觉统一到 Studio Console 体系（不再借用 whisper-theme）。
- 与现有「办公」agent（Hephaestus）、知识库/记忆中枢打通（复用不重建）。
- 旧 JSON 方案数据无损迁移。

非目标：
- 不改动其他板块（聊天/轻语/小说/绘梦/模型中心）。
- 不引入新框架/新运行时；不更换 Wails。
- **不实现**：图纸解析、清单解析、成本测算/商务报价、演示 PPT（由 gaea 其他板块后续迭代，本板块预留接口）。
- 不承诺商机监控、多用户 RBAC、云端同步（预留扩展点，不做实现）。

## 2. 现状审计结论

| 维度 | 现状 | 根本问题 |
|---|---|---|
| 数据模型 | 单个 Proposal JSON（`office/proposals/*.json`）+ 三级章节树 | 无项目/标段层级、无版本快照、无来源追踪、无法跨方案复用 |
| 领域知识 | `SoilRemediationKB` 硬编码字符串；规范检查单次 LLM 调用 | 规范库不成体系、不可维护；与知识库/记忆中枢未打通 |
| 招标解析 | 上传 → 转 Markdown → AI 分析 → JSON 文本框手改 | 无结构化字段卡、无「点击跳原文」定位、无 OCR（扫描件解析） |
| 大纲生成 | 单一「AI 生成大纲」 | 无目录生成依据策略、无字数/页数控制、无目录上传 |
| 撰写 | 章节流式撰写 + 润色 + Mermaid 图 | 无分章节批量生成与合并装配、无分节重写、无工艺流程图/组织架构图/横道图、无低雷同控制 |
| 校验 | 覆盖检查 + 规范检查（各一次 LLM 调用） | 无结构化规则（废标项/资质/工期/一致性/重复率/暗标格式） |
| 导出 | `docxAddMarkdown` 简单渲染 | 无模板排版、封面、页码、表格样式；无暗标规则；不能按章节导出 |
| 工作流 | 与「办公」agent 两张皮；商务报价/PPT 只存在于 agent 技能 | 文档编制与工具链（docx/xlsx/pptx/spec_query/cost_estimate 均已实现）无统一编排 |
| UI | 6 个 Tab 平铺，借用 whisper-theme 样式 | 无工作台感、无流程引导与阶段闸门 |

## 3. 调研结论（2026-08-05）

- **BidMaster-Pro**（开源全流程招投标 Agent）：LLM + RAG + Skill Engine 三引擎；4 阶段流水线（解读/生成/检查/排版）+ Gate Keeper 阶段闸门；21 项合规检查；历史标书/企业资料向量化；OCR（MinerU）；多 LLM 切换。
- **广联达云清标 AI 编标**：招标导入后自动解析基础信息/评分要求/废标项/格式与暗标要求，**双击可改、单击跳原文**；目录按「严格评标办法 / 严格格式要求 / 参考两者」三种策略生成；支持字数控制、上传目录；生成工艺流程图/组织架构图/横道图（对接斑马进度）；知识库参考历史标书；**暗标规则库**（全国地区）+ 导出格式设置。
- **Loopio / Responsive (RFPIO)**：内容库 = 单一事实源（文件夹/标签/权限），AI 推荐答案，评审工作流，到期跟踪。
- **易标 / 智标星**：标书查重、废标项检查、资质/工期/评分标准快速提取、一键定位原文。

结论：同类产品已把方案编写定义为「**解析 → 生成 → 检查 → 排版**的流水线 + 资产库复用 + 来源可追溯」。gaea 应借鉴其流程、规则与资产体系，而不是功能罗列。

## 4. 设计原则

1. **流程化**：四阶段流水线 + 阶段闸门，前一阶段未完成禁止进入下一阶段。
2. **数据先行**：结构化模型 + SQLite + 版本快照 + 来源追踪；旧 JSON 无损迁移。
3. **资产复用**：规范库、模板库、素材库、历史方案库四类资产，生成时自动引用。
4. **可追溯**：解析字段、检查结论、生成内容均可定位到招标文件原文或资产来源。
5. **规则可插拔**：目录策略、检查规则、暗标规则、导出模板均为可编辑配置，不是硬编码。
6. **复用不重建**：agent/tool/skill（spec_query、cost_estimate、docx/xlsx/pptx 等）与知识库/记忆中枢直接复用。

## 5. 分层架构（从底层到上层）

```
L7  工作流编排：四阶段流水线 + 阶段闸门 + 审阅流程（与办公 agent 打通）
L6  排版导出：docx 模板化 + 暗标规则库 + 按章节/全文导出
L5  校验引擎：结构化检查规则 + AI 辅助，输出检查报告
L4  生成引擎：目录策略 / 章节流式 / 分章节批量生成与合并 / 分节重写 / 图文与横道图
L3  知识资产：规范库 · 模板库 · 素材库 · 历史方案 RAG
L2  文档智能：多格式解析 + OCR 回退 + 结构化提取 + 来源定位
L1  数据底座：SQLite office schema + 文件存储 + 版本快照 + 旧数据迁移
```

### 5.1 L1 数据底座

**存储**：SQLite（`office.db`，复用 gaea db 迁移链模式）+ 文件目录 `dataRoot/office/{projects,proposals,files,exports}`。

核心表：

| 表 | 说明 |
|---|---|
| `projects` | 项目/标段：名称、分类（环保/市政/水利/建筑/其他）、客户、状态 |
| `proposals` | 方案文档：所属项目、类型（现阶段：技术标；预留：商务标/报价表/PPT）、模板、需求、状态、版本 |
| `sections` | 章节树：父级/层级/序号/标题/正文/字数目标/状态/来源引用 JSON |
| `files` | 附件：招标文件/参考材料（预留：图纸/清单），转换状态、OCR 状态 |
| `parse_results` | 结构化解析字段：字段名、值、来源文件/页码/片段、置信度 |
| `specs` | 规范条文库：标准号、条款号、内容、标签、适用域 |
| `templates` | 结构化方案模板：目录策略、默认章节、字数、图表要求 |
| `assets` | 素材库：业绩/人员/设备/常用段落，标签化 |
| `checks` | 检查结果：规则、状态、严重级、章节定位、证据 |
| `versions` | 版本快照：版本号、时间、差异摘要 |

**来源追踪**：`sources` 引用结构 `{fileId, page, start, end, snippet}`，贯穿解析字段 → 大纲 → 章节 → 检查证据。

**迁移**：读取旧 `office/proposals/index.json` 与各 `*.json`，每个旧方案自动挂到「未归档项目」，章节树原样导入，原始文件保留备份，只写新库不删旧数据。

### 5.2 L2 文档智能

- 解析管线：PDF/DOCX/TXT → Markdown（MarkItDown 优先，内置转换器回退）；扫描件 PDF 的 OCR 定义为可插拔接口（`OCRProvider`），P2 阶段先支持文字型 PDF，OCR 引擎接入列为独立后续任务，不绑定具体引擎。
- 结构化提取字段：项目概况、工期要求、资质要求、评分标准（评分项/分值/要求）、废标条款、格式要求、暗标要求。
- 每个字段记录来源定位（文件 + 页码 + 片段），前端单击跳原文、双击改值。
- 图纸解析、清单解析不纳入本板块（gaea 其他板块后续迭代），解析层预留 `ParseProvider` 扩展点即可。

### 5.3 L3 知识资产

- **规范库**：替代硬编码 `SoilRemediationKB`；初始覆盖土壤修复 HJ 25.1~25.4、GB 36600-2018、GB 15618-2018、HJ 1164-2021 等，条文级存储 + 全文/语义检索；`spec_query`/`spec_judge` 工具改读本库。
- **模板库**：模板 = 元数据 + 目录策略（严格评标办法/严格格式要求/参考两者）+ 默认章节 + 字数建议 + 图表要求；保留现有 8 个通用模板并升级土壤修复模板。
- **素材库**：业绩、人员、设备、常用段落；标签化管理，撰写时按需注入。
- **历史方案 RAG**：历史方案入库（复用 knowledge service 向量层），撰写时参考同类型方案降低雷同度。

### 5.4 L4 生成引擎

- **OutlineEngine**：按目录策略生成三级目录；支持字数/页数控制（一页≈800 字换算）、上传自有目录、增删改/重排后自动重编号。
- **SectionWriter**：章节流式撰写；上下文 = 解析结果 + 大纲 + 资产引用 + 已写章节 + 评分项；输出低雷同。
- **BatchWriter（批量生成引擎）**：15 万字级方案**不一次性生成**，按「章 → 节 → 小节」拆分为生成单元队列，逐单元生成并落盘，支持暂停/继续/重试/断点续写，全部完成后合并装配（详见 5.4.1）。
- **DiagramEngine**：工艺流程图、组织架构图、横道图/甘特图、常规 Mermaid 图；复用 `chart_gen`/`gantt_gen`，图节点可编辑。
- 商务报价/成本测算、PPT：不纳入本板块（gaea 其他板块后续迭代）。

### 5.4.1 长篇生成策略（15 万字级）

土壤修复投标技术方案通常约 15 万字，远超单次 LLM 生成与上下文能力，必须采用「**分章节生成 + 合并装配**」：

1. **字数预算分解**：总字数目标（默认 15 万，可配置）按评分权重/模板权重分配到章 → 节 → 小节；每节生成前带字数目标，超出/不足可预警。
2. **生成单元**：以「节/小节」为生成单元（单节约 2000–5000 字），「章」为组织单元；绝不把整章或全文作为一次生成输入。
3. **上下文注入（每单元固定预算）**：当前大纲节点 + 招标要点（评分项/废标项/工期/资质）+ 项目事实基线 + 相关资产（规范条文/业绩/素材）+ 前章摘要 + 后节锚点；不注入全量历史。
4. **项目事实基线（Project Facts）**：工期、工程量、人员、设备、单位名称、术语表在项目级维护，每章生成时统一注入，保证全篇一致；生成后由校验引擎做数据一致性复核。
5. **队列与断点续写**：批量生成 = 任务队列（生成单元粒度），支持暂停/继续/失败重试/断点续写；已生成单元实时落盘，失败不丢进度；进度事件沿用 proposal-stream 通道（当前单元/总单元、字数、耗时估算）。
6. **合并装配**：全部单元生成完成后，合并为完整 Markdown：目录生成、章节统一编号、图/表编号、交叉引用、附录整理；装配产物再进入 L5 检查与 L6 排版。
7. **衔接与防重复**：每个单元生成时注入前节结尾/后节开头锚点，检查阶段做跨章节重复检测与衔接检查（不重复、不断裂）。

### 5.5 L5 校验引擎

- `CheckRule` 接口 + 规则库，首批规则：评分点逐项覆盖、废标项对照、资质/工期一致性、前后数据一致性、重复率（低雷同）、规范条文引用、暗标格式（无彩色/加粗/特殊字符等）。
- LLM 作为「辅助规则」：负责语义判断，结构化规则负责可枚举判定；输出检查报告（状态/严重级/章节定位/证据），前端可逐项处理。

### 5.6 L6 排版导出

- docx 模板化排版：封面、目录、标题层级、字体/字号/行距、页码、页眉页脚、表格与图片样式。
- 暗标规则库：内置土壤修复常用暗标规则（全文无彩色/加粗/倾斜/下划线/目录/空行等），可编辑、可导入地区规则。
- 按章节导出 + 全文导出；格式 docx（主）/ md / pdf。

### 5.7 L7 工作流编排

- 四阶段：`interpret → generate → check → format`，阶段闸门（未完成解析不可生成等）。
- 与办公 agent 打通：Hephaestus 可通过 proposal 工具读写方案（新增 office 工具），沿用现有审批/审计（`office/audit_log.go`）。
- 审阅流程：批注/修订模式为 P8 范围，先做单人复核清单。

## 6. 前端设计

**布局**（三栏工作台 + 顶部流程条）：

```
┌────────────────────────────────────────────────────────────┐
│ 流程步骤条：导入解析 → 大纲 → 撰写 → 图表 → 检查 → 导出      │
├──────────┬─────────────────────────────┬──────────────────┤
│ 左栏      │ 中栏                          │ 右栏              │
│ 项目/方案  │ 目录树 + 文档编辑器            │ AI 助手上下文      │
│ 列表      │ （Markdown 编辑/预览 +        │ 招标要点/规范/资产/ │
│ 状态徽章   │  来源定位面板 + 检查面板）      │ 检查报告          │
├──────────┴─────────────────────────────┴──────────────────┤
│ 绑定模型卡（FeatureModelBar，保留）                         │
└────────────────────────────────────────────────────────────┘
```

- 左栏：项目 → 方案树，方案卡显示状态、模板、更新时间、检查分数。
- 中栏：目录树（新增同级/子级/删除/重排/上传目录）+ 编辑器（编辑/预览切换、F11 专注保留）+ 来源面板（解析字段/检查结论定位到正文与原文）。
- 右栏：AI 助手上下文（招标要点卡片、规范引用、资产引用、检查报告逐项处理）。
- 批量生成面板：队列进度（已生成单元/总单元、累计字数、耗时估算）、暂停/继续/重试/断点续写入口；单章可单独「批量生成本章」。
- 视觉：Studio Console 体系（主题令牌、状态点、分区标题、骨架屏、错误横幅、hover/press 反馈），移除 whisper-theme 引用与 emoji 图标。

## 7. 分期实施

| 期 | 内容 | 可交付成果 |
|---|---|---|
| P1 | 数据底座 + 项目化 | SQLite schema、项目/方案/章节/文件/版本、旧 JSON 无损迁移 |
| P2 | 招标解析管线 | 结构化提取 + 来源定位 + OCR 回退 |
| P3 | 大纲与撰写引擎 | 目录策略、字数预算分解、分章节批量生成队列（断点续写/合并装配）、分节重写、图文/横道图 |
| P4 | 知识资产库 | 规范库、素材库、历史方案 RAG |
| P5 | 校验引擎 | 规则化检查 + 检查报告 + 定位 |
| P6 | 排版导出 | docx 模板排版 + 暗标规则库 + 按章节导出 |
| P7 | 工作流编排 | 四阶段流水线 + 阶段闸门 + 与办公 agent 打通 |
| P8 | UI 工作台 | 三栏工作台 + 流程步骤条 + 审阅复核（Studio Console 体系） |

每期独立验收：`go test ./...` + `go vet` + `tsc` + `vite build` 全绿；P2 起每期附 CDP 全流程验证。

## 8. 风险与缓解

| 风险 | 概率 | 缓解 |
|---|---|---|
| 旧数据迁移破坏 | 低 | 只读旧 JSON、写入新库、保留备份、迁移后校验计数 |
| 大文档解析慢/失败 | 中 | 队列 + 进度事件（沿用 proposal-convert-progress）+ 分页提取 + OCR 回退 |
| LLM 输出不稳定 | 中 | 结构化输出 JSON Schema 校验 + 重试 + 人工确认（解析字段/大纲可改） |
| 暗标/排版规则复杂 | 中 | 规则库化，先内置通用土壤修复规则，后续可导入地区规则 |
| 长篇生成一致性/衔接差 | 中 | 项目事实基线统一注入 + 前章摘要/锚点 + 校验引擎衔接与重复检测 |
| 15 万字生成耗时长 | 中 | 队列化后台执行 + 进度事件 + 断点续写 + 单章批量生成，不阻塞编辑 |
| 范围失控 | 中 | 严格按 P1-P8 分期，每期独立验收；图纸/清单/成本测算明确划归其他板块 |

## 9. 默认决策（待用户审阅确认）

1. **商务报价/成本测算、图纸/清单解析、演示 PPT**：不属于本板块现阶段范围，由 gaea 其他板块后续迭代；本板块聚焦技术方案编写，仅预留接口。
2. **规范库初始范围**：土壤修复 HJ/GB 体系（HJ 25.1~25.4、GB 36600、GB 15618、HJ 1164 等）；市政/水利留待扩展。
3. **不做**：商机监控、多用户 RBAC、云端同步、移动端（仅预留接口）。
4. **视觉**：对齐 Studio Console（绘梦重设计）体系，不引入新 UI 框架。

## 10. 验收标准

- 全流程 demo：导入招标 PDF → 结构化解析并可跳原文 → 按评标办法生成大纲（含字数预算）→ 分章节批量生成 15 万字级方案（队列进度/断点续写）→ 合并装配 → 检查报告（覆盖/废标/暗标/一致性/重复率）→ 按暗标规则导出 docx。
- 旧方案 JSON 无损迁入新库，列表与章节完整可编辑。
- 规范库可检索并驱动 `spec_query`/`spec_judge`；生成内容可引用历史方案与素材。
- `go test ./...`、`go vet`、`tsc`、`vite build`、`wails build` 全绿。
