## 第 0 轮 · Codex → ZCode

**票型：B——只批一个最多六周、约 180 人时的 Case Kernel P0；暂不批“V5 唯一主轴”、12 个月全路线和 P1 起冻结。**

这不是否认 Case OS。代码审计足以证明 V4 的信任与执行底座必须先修；Case/Transaction/Evidence 也可能成为正确形态。争议在于：**“问题真实”不等于“当前这套解决方案、范围和时点已经该锁定”。**

### C1. 三个健康债应立即承认，但不自动推出 V5 整体立项

子代理审批放行、无 step 持久化、截断摘要当真值都是真实缺口。前两项直接破坏“可托付”，第三项破坏回滚正确性。它们应当进入同一 P0，而不是等到 V5 壳完成后再补。

但这也意味着 P0 的第一目标是**修复运行时可信度**，并非证明“事项”必须成为产品的唯一组织单位。把必要修复与一个尚未验证的 UI/信息架构绑定，会扩大沉没成本。

### C2. V4 组织方式“局部触顶”，不是已证明“整体错误”

阶段七已经落地任务收件箱，并把板块降为任务视图。真正缺的是事项级状态、验收、事务与证据连续性，而不是“用户仍只能从 13 个板块办事”这么简单。

若用户从任务收件箱进入，现有任务实体能否通过增加目标、验收、产物和账本满足需求？如果不能，具体是哪个真实工作流在第几步失败？提案没有给出这个对照实验。应先证明“富事项”比“现有任务 + 证据链”多创造什么，再确认它是否是唯一主轴。

### C3. 对个人工具，市场窗口不是主要决策依据

竞品、社区和 GitHub 研究能证明形态存在，不证明本项目现在应投入一年。当前治理明确产品化只是期权；若未来不做 SaaS、不融资、不为想象用户写代码，则“窗口正在关闭”不应成为投入 1,200–1,600 人时的理由。

决策尺子应是：真实任务是否更少返工、更容易签字、更可恢复，且用户愿意持续使用。提案当前连 V4 基线都未采，就设定效率提升 30%，因果链尚未闭合。

### C4. 686 绑定与 48 工具必须拆成三个指标

686 是 Wails RPC/维护面，不是模型一次能看到的工具集合。模型看到约 48 个内置工具。把“绑定数 ≤100”作为 V5 硬指标会同时误伤 UI 接口并掩盖真正问题。

建议拆开：

| 平面 | 决策问题 | 候选指标 |
|---|---|---|
| UI RPC | 维护成本、契约漂移 | 未使用绑定数、生成器一致性、App 编排抽离度 |
| Agent 可见能力 | 模型选择质量、权限与风险可治理性 | 单事项可见能力数、核心原语数、按事项动态挂载数 |
| 业务能力契约 | 副作用、幂等、证据、补偿可声明 | 契约覆盖率、无契约行动数、R3 绕过数 |

### C5. “没有 UI 也算成功”对个人工具不成立

无 UI 可以证明内核自洽，不能证明用户愿意把真实工作交给它。P0 至少应从现有任务收件箱或一个很薄的造价入口发起，由用户亲手完成一次真实案卷，且不得依赖开发者改库、手工补文件或 CLI 排障。

建议 P0 门槛：

1. 先用相同工艺跑 V4 基线，记录时间、token、返工、人工核对点和审批次数。
2. 12 份真实报价单全部可追到原始定位；无来源价格阻止结案。
3. 进程被强杀后恢复，不重复写入已提交效果。
4. 对受管文件回滚到导入前状态；回滚失败必须阻断而非报告成功。
5. 子代理危险写入和命令不能绕过审批。
6. 用户从现有壳或薄入口独立完成一次案卷，并在之后两周主动复用至少一次。
7. 不慢于 V4 且返工不增加；“下降 30%”可以留到 P1，不作为 P0 生存线。

### C6. 事件真相层尚未收口，不能先写出漂亮的投影

提案说 session log 是唯一真相，`case_events` 是可重建投影；但事项可以跨会话，当前又没有定义：

- 一条事项链由哪个 writer 串行追加；
- 两个并发子代理的事务如何排序；
- 崩溃时以文件日志、SQLite 投影还是受影响文件 hash 为准；
- 修复日志后，如何证明重建没有改变历史决策。

必须先做一页状态所有权设计并写失败测试，再决定是否保留逐事件哈希链。ZCode 提出“先 blob hash + before/after hash，链式哈希缓议”值得认真讨论，但无论是否上链，都不能保留双真相。

### C7. 应称“持久步骤 + Saga/补偿”，不要承诺泛化的 100% 回滚

本地文件、数据库行、外部 HTTP、命令执行和对外发布不是同一种可逆性。任何“所有 R2+ 产物回滚成功 100%”的指标若未限定受管效果范围，就是伪保证。不可逆或未知效果应阻断在 R3；可以补偿的受管效果才进入回滚率统计。

### C8. 六周 P0 可以批，12 个月与冻结暂不批

我建议把 P0 命名为 **Case Kernel / Trust Runtime Spike**，不先改产品版本号：

- 上限六周、约 180 人时；
- 只做造价一条垂直切片；
- 复用现有任务实体和壳，不先重造信息架构；
- 第 1 周采 V4 基线，第 2–5 周做可信执行与证据链，第 6 周真实 dogfood + 决议；
- 过关后再谈是否采用 Case 主轴、进入 P1、冻结哪些路线。

### C6 回应（D6）：一页状态所有权设计，现在给

1. **单 writer**：每 case 一个执行器 goroutine 独占串行追加权；子代理不直接写 `case_events`——向父执行器返回事务记录，父串行化落账。现状 session log 就是单写者模型（seq=已写行数），同构扩展。

### 3. 答你第三问：接受导出时链，但不得把自算哈希称作防篡改

接受 P0 不做写入时逐事件哈希链。单 principal 本地工具中，掌握 SQLite 和日志目录的同一写入者可以同时重算事件与链；没有外部锚点时，写入时链主要防意外损坏，不防“写入者改史”。这一威胁模型论证成立。

收窄为实现口径：

1. P0 必须有全文 before/after SHA-256、事务边界与导出清单；
2. 审计包导出时对有序事件生成哈希链或 Merkle root，并把 root 写进可打印回执；
3. 只有未来回执被外部审计、竣工资料或第三方依赖时，才增加数据库目录之外的锚点，例如用户签名、带时间戳的外部存证或另机归档；
4. 在缺外部锚点时，文案只能写“完整性与意外损坏检测”，不能写“可证明未被写入者篡改”。

因此，提案 §12.5 应从“账本采用哈希链/是”改写为：**P0 做内容 hash；导出做链；外部依赖时做签名/锚定。**

### 4. 一处需要纠正：V4 有两个不同的 task 系统

你在推理中将 `internal/gaea/db/schema.go:197` 的后台 `tasks` 表与阶段七任务收件箱放在同一张卡上讨论，这会打错靶。源码实际分为三个身份：

| 身份 | 实体 | 语义 | 证据 |
|---|---|---|---|
| 任务收件箱 | 单文件 JSON 建议队列 | pending/doing/done/abandoned；**无执行语义** | `internal/app/gaea_task_inbox.go:3`、`internal/gaea/tasks/tasks.go:41` |
| 后台作业 | SQLite `tasks` 表 | queued/running/succeeded/failed，进度与重试 | `internal/gaea/db/schema.go:192-212` |
| DAG 节点 | 办公流水线的步骤 | 会派生子会话执行，有节点状态 | `docs/gaea-office-dag-63-design-2026-09.md` |

纠正后，你的主结论仍然成立：任务收件箱可以当“壳”，因为它本来就自陈无执行语义；后台 `tasks` 表也不能承担事项验收；运行时仍缺统一步骤、事务、证据与审批域。**所以第一版应复用任务收件箱做薄入口，而不是把后台任务表改造成 Case。**

### 5. 跨会话状态所有权：接受，但加一道提交屏障

接受“每 case 单执行器 writer、子代理只回记录、父执行器按提交序落账、文件 hash 参与崩溃裁定”。为消除“三份真相”的歧义，补一个状态机约束：

```text
intent_recorded
  → effect_observed（before/after hash 可核）
  → transaction.committed（写 case_events）
  → projection.updated（SQLite 查询视图）
```

规则：

- 未观察并核对效果，不得追加 `transaction.committed`；
- 崩溃在 effect 与 commit 之间时，reconciler 必须追加显式 `transaction.reconciled` 事件，再补提交或标记 abort；
- `steps/effects` 是执行域事实，`session log` 是对话域事实；case 层的权威不是二选一，而是“两域事实经 reconciler 后形成唯一 commit 事件”；
- replay 必须把 `transaction.reconciled` 当正式历史，不得事后静默修平差异。

这样“单一事实源”可准确表述为：**每个域一个写者；跨域由一个显式对账事件收口。**
