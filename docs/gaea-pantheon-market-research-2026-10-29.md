# Gaea「众神殿」市场调研与产品判断

> 日期：2026-10-29 · 状态：调研完成，MVP 已实现 · 范围：市场调研 + 首版生产接线
>
> 需求假设：在 Gaea 增加一个一级板块「众神殿」，调用本机 Codex、ZCode、DSH 等 Agent，对一个议题独立研判、交叉质询并形成最终结论。
>
> **2026-10-29 用户修订（优先于下文早期产品假设）**：众神殿应成为公正、客观、协助、互助的多轮圆桌讨论，而不是裁决法庭。用户可指定发言顺序；默认至少两轮，后续轮次自动轮换首位；参与者承接前文、补充证据、澄清分歧和修正观点，主持席位只负责协作综合，不评胜负。本文后续的「四阶段」「质询」「裁决」等段落保留为调研历史，实际实现以第 12 节为准。
>
> 本文结论基于公开产品文档、GitHub README、论文摘要，以及本机安装与 Gaea 现状核验。订阅套餐、CLI 参数和竞品功能变化很快，进入实现前应以当日版本重跑适配探针。

---

## 0. 结论

**建议：有条件进入产品定义，暂不直接进入全量实现。**

市场不是空白。Karpathy 的 LLM Council、DSH Council、Agent Council、Quorum、AgentPipe、OpenRouter Fusion 已经分别验证了「多模型独立回答、互评、主席综合」和「本机 Agent CLI 协作」两种基本形态。如果众神殿只做三个模型轮流发言，它会很快变成已有开源工具的可视化外壳。

仍然存在一个明确空位：

> **把本机异构 Agent 当作不同判断主体，而不是同一种模型 API；围绕一份共同证据包进行结构化辩论，最终留下可复核、可导出、可继续追问的议事录。**

一句话定位：

> **众神殿不是模型竞技场，也不是聊天板块的第二入口；它把重要议题交给本机众 Agent 议事，最后由证据和人来收口。**

首个版本只批准以下范围：

1. 一级板块 + 议题列表 + 一次议事；
2. Codex、ZCode、DSH 三个初始Adapter；
3. 「独立陈词 → 匿名互评 → 质询/修订 → 首席裁决」一条协议；
4. 共同材料、约束、模型/Harness 身份、原始回答、分歧、引用和成本可见；
5. 只读运行、可暂停/终止、超时隔离、失败如实展示；
6. 导出 Markdown/JSON 议事录。

暂不做：开放回合制社交聊天、自动执行代码修改、Agent 排行市场、无限自由辩论、把多个订阅凭证抽出来做统一代理。

## 2. Gaea 现状与落点

### 2.1 为什么适合做一级板块

Gaea 已有三类可用资产：

1. **本机执行环境**：Codex CLI 在 PATH 中；ZCode 与 DeepSeek Harness 桌面版已安装。ZCode 源码提供 `--prompt`、`stream-json` 和 `app-server --stdio`；DSH 源码提供 headless profile 与 ACP/SDK 入口。接入不必依赖屏幕自动化。
2. **材料与记忆**：办公工作区、知识库、造价库、项目记忆和附件选择可以组成共同证据包。
3. **产物与记录**：已有产物面板、任务记录和 Markdown/文件导出能力，可把议事结果变成正式文件，而不是丢在聊天里。

众神殿面向「重要但不确定」的问题，组织对象是**议题**，不是会话。因此它与聊天、办公、造价、记忆中枢不是同一类使用路径，有资格成为一级入口。

### 2.2 需要正视的现有约束

- 当前 Gaea 的长期治理倾向「少加新板块」，且明确定位是个人工具、产品化只是期权。本次用户已明确要求新增一级板块，属于直接指令覆盖默认倾向；但仍应让首版证明它不是一个空入口。
- 现有 `task` / DAG / `run_skill` 更偏执行编排：一个父 Agent 派工，子 Agent 回来交结果。众神殿需要的是**观点独立、可冲突、可保留异议**，不能简单复用父 Agent 统一上下文。
- 子代理无交互审批时的放行问题曾在项目审计中被列为健康债。众神殿默认只读，不把「多个外部 Agent 都能改工作区」作为卖点；任何写操作应另走显式授权。
- 一级导航应归属 `shared` 空间，但每个议题必须自行选择证据范围。跨工作/乐园材料只能由用户显式加入，不能借众神殿绕过空间隔离。

## 3. 市场格局

### 3.1 代表产品与真实能力

| 产品 | 形态 | 已证明的能力 | 众神殿可借鉴 | 留下的空位 |
|---|---|---|---|---|
| **LLM Council**（Karpathy） | 本地 Web 小应用 | 多模型独立回答 → 匿名互评排序 → Chairman 综合；截至 2026-10-29 约 2.6 万 stars | 三阶段协议、匿名互评、个体答案可检查 | 作者明确声明是实验性 hack、不维护；依赖 OpenRouter API，不是本机异构 Agent |
| **DSH Council** | DSH 插件 | 2–8 个回答者并行、1–8 个审阅者、1 个裁决者；输出共识、分歧、盲区、置信说明，原始记录留在子会话 | 角色分离、盲区检测、结果可检查 | 仅覆盖 DSH 配置内的模型，不是跨 Harness；没有 Gaea 工作区/文档/记忆一体化 |
| **Agent Council** | Codex/Claude 技能 + Shell | 并行调用本机已安装的 Codex、Gemini、Claude 等 CLI，再由主席综合；明确强调复用本机订阅，不额外买 API | 本机 CLI 适配器、并行、主席汇总 | 轻量脚本，无正式 UI、无共同证据工作台、无长期议事状态与验收 |
| **Quorum** | 终端/Web 辩论工具 + Codex/Claude 插件 | 支持 Standard、Oxford、Advocate、Socratic、Delphi、Brainstorm、Tradeoff 七种方法；可混合本机 Agent CLI、API 模型与 Ollama；保存与导出运行记录 | 辩论方法与角色不应只有一种；本机 CLI 可被统一编排 | 仍是独立工具；没有 Gaea 的材料/产物/知识库；默认摘要式辩论，不足以构成可签字裁决 |
| **AgentPipe** | CLI/TUI 多 Agent 房间 | 多 CLI 在同一房间轮流、响应式或自由对话；有成本、耗时、导出和恢复 | 共享房间、运行指标、会话导出 | 偏聊天；其 Codex 适配器使用绕过审批/沙箱的参数，不适合被 Gaea 直接照搬 |
| **OpenRouter Fusion** | 云端路由器 | 1–8 个 panel 模型并行回答，analyst 输出共识、矛盾、覆盖缺口、独特洞见和盲区，由外层模型形成最终答案；官方说明默认 3 模型约 4–5 倍单次成本 | 结构化分析 JSON、盲区字段、按需触发、成本提示 | 云 API 与模型层面，不是本机 Agent；身份与应用上下文有限 |
| **AWS CLI Agent Orchestrator** | 本地服务 + supervisor + tmux | 管理多个原生 CLI 进程，主管把任务分派给专家并行或串行；具备工作区、MCP、Web UI | 进程隔离、健康检查、会话恢复、原生 CLI 能力保留 | 目标是把活做完，不是把不同判断摊开辩论 |
| **Pane** | 跨平台 CLI Agent 管理器 | 统一管理任意 CLI Agent 的并行会话与工作区 | Agent 探测、会话管理、跨平台 UI | 仍是执行管理器，缺少审议协议与决策产物 |
| **Arena.ai（原 LMArena）** | 公开模型评测平台 | 官方定位是 AI evaluation/ranking，提供并排比较、排行榜、Agent 等评测入口 | 并排比较、匿名盲测、评测意识 | 目标是评价模型，不是替用户形成一项可执行决定 |
| **TradingAgents** | 金融多 Agent 框架 | 让分析师、牛熊研究员、交易员和风控以角色分工辩论，支持可追溯投资决策 | 角色化分歧、专业视角、结论可回看 | 只适配金融；角色是模拟人格，不证明通用议题上能提高正确率 |

### 3.2 竞品横向判断

市场已经商品化的是三层能力：

1. **并行问多个模型**：API、Panel、Arena、LLM Council 都已做到。
2. **本机 CLI 统一启动**：Agent Council、Quorum、AgentPipe、CAO、Pane 都能做一部分。
3. **匿名互评与主席综合**：LLM Council、DSH Council、OpenRouter Fusion 已经把它变成标准配方。

尚未形成清晰产品的是：

1. **跨 Harness 的身份与能力差异**：Codex、ZCode、DSH 不只是三个模型，它们有不同的系统提示、工具、记忆、权限和失败方式。
2. **以证据为中心的裁决**：多数产品只让模型互评语言质量，没有把共同材料、定位、引用和人工验收纳入最终结论。
3. **议事资产化**：一次辩论结束后，问题、立场变化、未解分歧、证据和后续决定通常不进入可复用账本。
4. **本地桌面中的可操作界面**：终端工具强，但用户难以在同一个界面里选材料、观察过程、追问、裁剪证据并把结论交给办公产物。

### 3.3 直接威胁判断

- **DSH Council 是最直接的「协议威胁」**：如果用户已经在 DSH 内工作，它已覆盖大部分独立回答、互评和裁决体验。
- **Quorum 是最直接的「CLI 编排威胁」**：它已经混合本机 Agent CLI、本地模型和多种正式辩论方法。
- **Agent Council 是最直接的「低成本复制威胁」**：一个技能包即可调用已安装 CLI，证明技术门槛不高。

因此众神殿不能以「支持三种 Agent」为护城河。它能成立的理由必须是：

> **Gaea 的项目上下文 + 共同证据包 + 跨 Harness 议会 + 可复核裁决 + 产物化。**

## 4. 学术证据：辩论不是默认更聪明

| 研究 | 结论 | 对产品的要求 |
|---|---|---|
| *Improving Factuality and Reasoning in Language Models through Multiagent Debate*（2023） | 多实例提出理由并多轮辩论，可提升数学、策略推理和事实有效性，减少幻觉。 | 辩论机制值得保留，但必须让过程可检查，而不是只存最终答案。 |
| *Should we be going MAD?*（2023） | 当前多 Agent 辩论不总能稳定超过 self-consistency 或多路径集成；对超参数和协议非常敏感。 | 默认基线必须是「独立回答 + 多数投票/集成」，不能用自由聊天替代。 |
| *Debate or Vote?*（NeurIPS 2025 Spotlight） | 多数投票解释了 MAD 的大部分收益；在无偏随机过程假设下，辩论本身不提高期望正确率；需要偏向纠错/验证的干预。 | 裁决要能引用证据并明确纠错，而不是让模型互相说服。 |
| *When Debate Helps*（2026-10） | 辩论超过投票需要两个条件：提案供给中有正确答案，且读出/裁决能识别正确证据；多样性覆盖和验证感知缺一不可。 | 参与者要真正不同；每轮要有证据核验、独立立场和明确读出规则。 |

### 4.1 产品结论

必须同时支持三种可比较路径：

1. 单个最佳 Agent 直接回答；
2. 多 Agent 独立回答 + 投票/集成；
3. 多 Agent 互评/质询 + 证据裁决。

众神殿应默认从第 1/2 种起步，在用户认为「代价远高于多跑几次」时才升级到第 3 种。每次运行都记录使用了哪条路径，后续才能知道辩论是否真的值得。

### 4.2 成功门槛

首轮产品验证不能只看「看起来讨论得很热闹」。建议以 20–30 个真实议题对照：

- 裁决被用户接受的比例；
- 事实错误与来源缺失率；
- 发现了多少个单 Agent 漏掉的**有效**观点；
- 是否保留了少数但正确的异议；
- 到结论的时间和总调用成本；
- 用户是否愿意第二次主动使用，而不是被演示吸引一次。

若完整辩论不能稳定优于「独立回答 + 投票/综合」，就应缩成「多 Agent 会诊」，而不是继续增加轮次。

## 5. 用户任务

### 5.1 最适合的任务

| 场景 | 为什么值得多 Agent |
|---|---|
| 技术选型与架构取舍 | 不同 Harness 对风险、实现成本、可维护性的盲区不同 |
| 方案/合同/投标口径复核 | 需要发现冲突、遗漏和不可逆风险 |
| 重要文档的审阅与反方意见 | 单 Agent 容易顺从作者或先验结论 |
| 多来源研究结论汇总 | 需要区分共识、矛盾、证据强弱与覆盖缺口 |
| 长篇创作关键转折评审 | 可同时检查人物一致性、主题、节奏与平台风险 |
| 多个模型结论不一致时的二次判断 | 用户真正关心的是「为什么不同、哪个有证据」 |

### 5.2 不适合的任务

- 随手一问的事实查询；
- 已经能由确定性程序算出的结果；
- 直接编码并修改文件；
- 纯模型跑分或排行榜；
- 没有标准、只要创意的无限头脑风暴；
- 用户不愿提供必要材料、却期待「多个模型互相猜」得到可靠结论。

## 6. 产品定义

### 6.1 核心对象

| 对象 | 数据 | 说明 |
|---|---|---|
| 议题 | 标题、问题、目标、约束、决策标准、截止时间 | 一个可被讨论和裁决的问题 |
| 材料包 | 文件、片段、URL、知识条目、来源 hash | 所有参与者共享的同一事实基线 |
| 参与者 | Harness、模型、角色、权限、版本、健康状态 | 不只是「Codex/ZCode/DSH」，要记录实际模型与会话能力 |
| 轮次 | 陈词、审阅、质询、修订、裁决 | 每轮输入输出均可回看 |
| 立场 | 结论、置信度、关键假设、证据引用、未解决问题 | 结构化，不用纯自然语言埋在大段文本里 |
| 裁决 | 推荐、条件、备选、反对意见、证据、人工签注 | 可导出为正式文件 |
| 议事录 | 全事件的追加式记录 | 支持恢复、审计和继续追问 |

### 6.2 推荐首版协议

```text
设坛
  ├─ 写清议题、目标、约束、成功标准
  ├─ 选择材料包与允许的来源
  ├─ 选择参与者、角色、权限和预算
  └─ 选择裁决者与人工门槛

第一幕 · 独立陈词
  ├─ 各 Agent 在隔离上下文中并行回答
  ├─ 先不暴露其他答案，避免锚定
  └─ 输出：结论、前提、证据、置信度、异议点

第二幕 · 匿名互评
  ├─ 隐去 Agent 名，仅显示 A/B/C
  ├─ 评估准确性、证据、遗漏、可执行性
  └─ 标记“正确但少数”的观点，避免简单多数碾压

第三幕 · 定向质询
  ├─ 只围绕关键分歧与证据冲突追问
  ├─ 默认最多两轮，可随时暂停或人工插话
  └─ 每轮必须回答：我改变了什么、为什么、依据是什么

第四幕 · 裁决
  ├─ 先做证据核验，再做综合
  ├─ 输出推荐、适用条件、反例、未解风险
  ├─ 保留异议与失败/超时的 Agent
  └─ 用户签注后才成为正式结论
```

关键设计：**先独立，后交换上下文**。如果一开始就共享同一段对话，参与者会迅速趋同，得到的只是「三个模型的同一种幻觉」。

### 6.3 后续模式

首个闭环跑通后，再按任务增加：

- **正反辩**：适合二选一决策；
- **红队审议**：指定一名参与者专门攻击主流结论；
- **德尔菲估算**：匿名多轮修正工期/成本/概率；
- **圆桌角色**：产品、安全、法律、工程等不同视角；
- **快速会诊**：只做独立回答与综合，不进入多轮辩论。

不要首版同时做七种方法。方法多并不等于判断可靠，反而会稀释交互设计和成本控制。

## 7. 信息架构与交互建议

### 7.1 一级入口

建议定位为 `shared` 空间的一级板块：

- 名称：**众神殿**
- 主语：**议题**
- 核心动作：**设坛 / 开议 / 裁决**
- 内容层继续中文单语，壳层沿用现有三语规则。

不建议叫「模型比较」或「多模型聊天」，否则会和模型中心、聊天板块争抢职责。

### 7.2 页面骨架

```text
众神殿
├─ 左：议题列表
│  ├─ 草稿
│  ├─ 进行中
│  ├─ 待裁决
│  └─ 已归档
├─ 中：议事台
│  ├─ 议题与约束
│  ├─ 参与者席位
│  ├─ 当前轮次与议事流
│  └─ 人工介入栏
└─ 右：卷宗检查器
   ├─ 材料与引用
   ├─ 观点差异
   ├─ 证据缺口
   ├─ 成本与耗时
   └─ 最终裁决
```

### 7.3 三个关键界面状态

**设坛**

- 先写「要决定什么」，再选 Agent；不能反过来让用户先玩模型。
- 材料篮显示哪些内容会发送给云端参与者，避免「本地优先」被误解为数据不出机。
- 显示调用预算：参与者数 × 轮数 × 可能的重试，允许用户限制调用次数、Token 和等待时间。

**开议**

- 每个席位展示 Harness、实际模型、角色、状态、耗时和当前动作。
- 默认使用功能性标签（陈词/审阅/裁决），神话命名只做气质层，避免用户看不懂流程。
- 支持暂停全部、中断单个 Agent、补充一条证据、要求某位解释某个引用。
- 对失败、超时、未认证分别显示原因；不要静默用另一个 Agent 顶替身份。

**裁决**

- 首屏不是一大段「综合意见」，而是四块：推荐、适用条件、主要分歧、未解风险。
- 每条关键结论可回溯到原始发言和证据定位。
- 「共识」与「一致」分开：前者是共同支持，后者可能只是上下文趋同。
- 用户可采纳、修改、否决或要求再审；人工签注比模型置信度更可信。

### 7.4 匿名互评的边界

在审阅阶段隐藏 Harness/模型名，能降低品牌偏见；但在结果页必须还原身份，否则无法复盘「某人为什么总在某类问题上失败」。匿名只服务于公平评分，不服务于抹除来源。

## 8. 差异化

### 8.1 已有能力不是壁垒

以下能力都已出现在竞品中，只应视为必要条件：

- 并行问多个模型；
- 多轮讨论；
- 匿名互评；
- 主席综合；
- 本机 CLI 调用；
- 成本/耗时显示；
- Markdown/JSON 导出。

### 8.2 真正可防守的组合

1. **异构 Agent 而非同构模型**：Codex、ZCode、DSH 带着不同 Harness、工具和失败模式入场；用户要看到的是判断主体，不只是模型名。
2. **证据约束**：共同材料包、引用定位、来源 hash、证据缺口进入裁决结构。
3. **人机共裁**：主席只提出裁决建议，用户签注才结案；异议和反例永久保留。
4. **议事到产物**：裁决可直接进入办公文档、造价复核、报告或知识库，而不是停留在工具输出。
5. **本地运行账本**：保留调用、身份、版本、输入范围和结果；支持故障恢复与离线回看。
6. **安全默认值**：只读、超时、取消、按 Agent 隔离权限；不靠自动批准换取「流畅」。

## 9. 风险与产品防线

| 风险 | 表现 | 防线 |
|---|---|---|
| 伪共识 | 多个 Agent 互相影响后都说同一件事 | 先独立陈词；匿名互评；保留原始立场 |
| 辩论越多越错 | 错误观点被重复强化，成本上升 | 证据核验优先；最多两轮定向质询；与投票基线对照 |
| Agent 同质化 | 三个 Harness 默认同一家大模型 | 允许用户选模型，界面明确实际模型与角色 |
| 订阅/协议风险 | 抽取凭证、反向代理订阅、绕过供应商限制 | 只通过已安装官方 CLI/标准协议普通调用；不导出凭证；失败如实报告 |
| 数据外发 | 材料被多个云模型同时读取 | 发送前显示目的地；支持 local-only 过滤；逐 Agent 权限 |
| 命令/文件事故 | 多 Agent 同时修改工作区 | 众神殿 v1 只读；写操作需单独授权与事项范围 |
| CLI 漂移 | 参数、JSON schema、认证变化 | 版本化 Adapter + 健康探针 + 明确不可用态 |
| 成本失控 | N 个 Agent × M 轮 × 重试 | 预算上限、熔断、并行/串行策略、调用账本 |
| 输出不可复核 | 只有长篇综合，没有证据定位 | 结构化裁决字段；关键结论一律附来源或标「推断」 |
| 导航膨胀 | 成为第三个聊天入口 | 首版只做完整议事闭环；持续记录使用与复用证据 |

### 9.1 技术接入底线

- 优先使用 Codex `exec`/结构化输出、ZCode `--prompt`/`stream-json`/app-server、DSH headless/SDK 等正式入口。
- 不把桌面 UI 自动化当作 Adapter 主路线；只有官方无头入口确实不存在时，才考虑受限桥接。
- 每次启动先探测可执行文件、版本、认证、能力与输出协议；能力不明时 fail-closed。
- 子进程必须有超时、取消、输出上限、进程树回收和脱敏日志。
- 众神殿的统一账本记录的是**调用事实**，不把各 Agent 自己的内部缓存当共享记忆。

## 11. 最终判断

### 推荐

**有条件做。**

众神殿能补上 Gaea 当前没有的「重要议题审议」主场，而且与本地 Agent、本项目材料、办公产物天然相连。一级入口成立，但必须把它设计成一个**有证据、有分歧、有裁决、有留痕**的议事台。

### 不推荐

- 只做多模型并排回答；
- 让多个 Agent 无边界自由聊天；
- 以「三个 Agent 都同意」作为正确性保证；
- 为了调用成功默认关闭权限或绕过沙箱；
- 首版铺开七八种辩论模式。

### 下一步

市场调研阶段到此结束后，用户已拍板先实现首版。实现范围与验证见下一节；后续产品门仍应以真实议题对照为依据，不因「能跑」自动宣判辩论优于投票。

首版已知边界：

- 工作空间选择已接入 Agent cwd 和议事简报，但外部 CLI 是否能严格限制越界读取仍取决于其自身 sandbox/plan/read-only 实现，不能把 cwd 当成完整文件系统沙箱；
- 外部 CLI 若只在进程结束时输出一次性 JSON，Gaea 仍只能在消息到达后分段呈现，无法获得其未暴露的 token 级事件；
- 只读是 Adapter 的首要边界，但外部 Agent 自身版本/配置变化仍需持续探针；
- DSH 需从当前 Gaea 工作区解析其 `.env`/配置层；缺失凭据时如实显示失败，不由 Gaea 代填密钥。

### 续优化记录（2026-10-29）

- **结果优先**：已完成/失败会话先呈现协作小结或失败说明，再展示共享观点池、独立窗口与时间线，避免用户为了看结论先翻阅整个过程。
- **续议闭环**：从小结生成新议题草稿，带入上一轮综合建议、保留分歧、风险、原始材料、工作空间、参与者和发言顺序。它明确标注“续议依据”，不冒充对上一场完整内部上下文的自动继承。
- **导出补齐**：Markdown 用于阅读归档，JSON 保留完整 request / participants / events / contributions / verdict / signoff，满足调研阶段要求的结构化议事录。
- **历史检索**：本地档案可按标题、工作空间、结论和错误文字搜索，并可筛选进行中/已结束；不改后端数据形状。
- **档案栏折叠**：桌面档案栏可收为 72px 窄轨，保留新建、数量、展开入口与 Agent 状态；状态写入 `localStorage`。移动端不复用窄轨，继续使用横向档案卡。
- **轮次模式**：手动模式支持填写 2-20 轮；不限模式要求每席在补充论证末尾声明“一致”或“仍有分歧”，只有所有实际参与者都明确一致时才提前结束。无共识时默认安全上限 12 轮，达到上限后保留分歧并继续协作汇总，防止无限调用。自动模式使用三段式轨道，手动高轮次使用横向滚动轨道。
- **Agent 工具**：Codex、ZCode、DSH 均可使用各 Harness 提供的工具。Codex 在只读 sandbox 中执行；ZCode 使用 plan 模式与 `stream-json`；DSH 使用 read-only permission。Grok 由 Gaea 办公 AgentRunner 驱动，每轮按议事工作空间新建只读注册表，复用文件读取、搜索、造价、知识、记忆与日程工具；`write_file/edit_file/bash/task/install_skill` 等写类或编排类工具不会暴露，xAI 调用仍记入 `pantheon` feature。
- **实时轨迹**：统一解析 Codex `item.started/completed`、ZCode `tool_call/tool.updated`、DSH `tool_call/tool_result`，在讨论页以工具卡片实时展示 Agent、工具名、状态、输入摘要与可展开的结果预览。模型内部 reasoning 不进入工具轨迹，避免把思维流误当成工具日志。
- **工具边界**：讨论提示词要求外部 Agent 仅在必要时使用只读读文件、搜索或命令核验证据，禁止写盘、改配置、安装软件、启动副作用服务或读取凭证；所有输出预览均有长度上限。
- **操作可解释**：发起页桌面操作栏吸底，阻塞时直接显示缺少工作空间、参与者不足或议题为空；移动端回到正常文档流，防止大尺寸控制面板遮挡正文。
- **长上下文安全**：提示词超过预算时保留开头事实基线与末尾本轮任务/输出契约，中段裁切会留下显式标记，避免历史越长越容易丢掉 JSON 格式要求。
- **崩溃恢复**：应用启动时会把上一进程遗留的 `running` 会话转为 `failed`，保留已有发言与事件，并把仍在运行中的参与者标记为中断；恢复操作幂等。
- **验证**：众神殿前端 18 例、发布前全量本地快闸全绿（Go build/vet/lint/全仓测试 + 465 文件/4053 例前端测试 + 生产构建 + E/文档守卫）、`internal/pantheon` 全包（含跨供应商工具解析、轨迹持久化、轮次归一、共识提前结束与安全上限）、`internal/app` Pantheon/Grok 定向、TypeScript、ESLint、`go vet` 均通过；390/720/1440 与亮暗主题目检通过；Codex 0.165.0、ZCode 0.17.0、DSH 0.2.1-rc.3 最小只读工具探针通过；绑定面仍为 11 个 `PantheonB` 方法，无契约漂移。race 检查因本机缺 gcc/CGO 环境未执行。
