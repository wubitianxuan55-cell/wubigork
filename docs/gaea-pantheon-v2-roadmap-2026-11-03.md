## 主线判断(四席多轮收敛,无一席反对)

校正、留异议、收口是三件不同的事;本轮改造前,实现把三者都压在「自然语言发言流+
末端汇总」上,结构化只发生在最后一刻,不回灌轮次。外部研究(Codex r9 双源复核+仓内
docs/gaea-pantheon-market-research-2026-10-29.md 交叉):**自由多轮辩论不稳定优于
独立作答+集成**——辩论轮的价值在证据校正,不在多聊。

## 执行摘要

1. **四个上游都不接成众神殿内核。** 它们是四个不同层级的参考:研究台、会议交互、
   独立评审、执行协作。众神殿吸收的是职责分离与可审计字段,不是代码依赖。
2. **默认仍是「独立开场 → 圆桌讨论 → 协作综合 → 人工签注」。** 不把长辩论、
   投票或陪审团设成默认;先证明它们在具体议题上有增益,再开放。
3. **下一阶段最重要的缺口不是再写更强的辩论 prompt,而是让“讨论动作”可核查。**
   当前能看见一段发言,仍看不清它是在提出主张、质疑某条论证、回应质疑、修正立场,
   还是只是补充背景。
4. **分歧台账已经是正确的机制支点。** 下一步把动作、目标贡献 ID、回应结论与
   “下一轮是否真能减少不确定性”接到同一台账上,让每轮讨论有可验证的推进物。
5. **高保障模式采用独立确认,不做 Agent 排行榜。** 结论生成者与结论检查者职责分离;
   反对意见按主张与证据保留,不按 Agent 品牌或字数评分。
6. **执行属于签注后的另一产品面。** 当前只做到结构化行动提案;写入、派工和外部副作用
   必须另立授权、工作区、预算与验收。

一句话方案:

> **保留众神殿的圆桌气质,补上辩论框架的机制骨头:动作明确、目标可寻、
> 异议可闭合、收口有判据、结论可独立复核、执行须另签。**

## 四框架对照与取舍

### MALLM:把协议当变量,不是把选项全铺给用户

核验快照:`Multi-Agent-LLMs/mallm@eeec9f5c28961a7349cbb4306a5aa860bdaef6dd`,
ACL EMNLP 2025 Demo。

它把 MAD 拆成四个可组合维度:

- Agent persona:参与者是谁;
- response generator:怎样表达,例如 simple、critical、reasoning;
- discussion paradigm:信息如何流动,例如 memory、relay、report、debate、
  collective refinement;
- decision protocol:怎样结束和读出,包括投票、阈值共识、全体一致、裁判等。

**吸收:** 把“开场可见性、轮次推进、讨论动作、最终读出”拆成独立变量;保存配置、
消息、轮次与结果,支持单变量对照评测。

**不吸收:** 144 种组合是研究空间,不是产品信息架构;把组合矩阵直接铺进众神殿会
让用户替产品承担协议设计工作。也不能把上游实验结论当作 Gaea 异构 Harness 上的
效果保证。

**落点:** `StartRequest.Protocol` 继续只承担“首轮是否可见同轮前序”;新增能力必须
用独立字段表达,不再让一个字符串同时暗示轮次、动作和裁决。

### Captain Claw / Agent Council:让讨论动作和议程显式

核验快照:PyPI `captain-claw 0.4.17` 与 GitHub
`kstevica/captain-claw@f5f2805c47d39b2cb4ff70f445f61f12cd549948`(0.8.5)。

其议事模型包含:

- Debate、Brainstorm、Review、Planning 等会议类型;
- 每席自报 `SUITABILITY`,选择 `answer / respond / challenge / refine / broaden / pass`;
- Round-robin 或 Moderator 选择下一位;
- 主持人综合后,所有席以 agree / disagree / abstain 加理由确认;
- 导出含 TL;DR、投票、行动项的 Markdown 纪要。

**吸收:** 动作类型、目标贡献、主持议程、结论确认、纪要资产。

**不吸收:** 默认让模型自评 suitability 决定话语权;把 agree 多数当事实真相;
把参会者投票包装成胜率;从议事直接自动生成并执行外部任务。

**落点:** 动作进入 `Contribution`,目标必须指向已知贡献 ID;主席只维护议程与
分歧,不排名;确认以“愿不愿意签这一版结论”表达,而不是“哪一席赢了”。

### ARTEMIS:生成者不等于复核者

核验快照:`bassrehab/artemis-agents@599e66ff9ca12475f86a8bb41672a5b6279b570f`,
PyPI `artemis-agents 2.0.0`。

其流程把开场陈述、主辩论、结案陈述和陪审团评审分开,保留异议、置信度与评分明细。
真正值得吸收的是职责分离;其自带评分大量依赖连接词、正则、长度和强调词,
置信度是启发式合成,且官方来源是 Technical Disclosure,不能当同行评审的客观裁判。
其 86% 自测只有 3 个议题 × 3 次 × 3 框架,benchmark 中实际仅 1 名陪审员。

**吸收:** 结论生成与读出分离;复核者独立工作;异议显式保留;高影响决定可多视角检查。

**不吸收:** Agent 排名、关键词式“逻辑分”、未校准 confidence、以 winner-of-agents
代替 truth-of-claims。

**落点:** 先做可选的“签注前独立自检”。每席面对冻结后的结论与台账,回答
“支持 / 有条件支持 / 反对”及理由;系统不合成团队分数,只保留阻塞异议与修订依据。

### AgentTeams:裁决之后才进入执行协作

核验快照:`agentscope-ai/AgentTeams@d9366ac43a153d31c73ef4def125e378869b8d85`。

它以 Matrix 房间承载 Human、Manager、Team Leader 与 Worker 的可见协作,任务有状态、
依赖、结果和人工插入;模型与 MCP 凭证由网关隔离。它解决的是“把活可靠地做完”,
不是“哪种判断更可信”。

**吸收:** 行动账本、可见的人工干预、任务依赖、验收证据、幂等派工。

**不吸收:** 为桌面议事引入 Matrix/Kubernetes/MinIO 全套基础设施;让 Manager
不进入 Team Room 的层级边界污染辩论阶段;在议事读取权限外偷偷执行写操作。

**落点:** `Verdict` 可附带只读行动提案;用户签注后,未来另行进入“事工房”模式,
重新确认工作区、写权限、预算和执行者。

## 目标模型:四个正交维度

内部实现可以表达为四层,用户只看到少量命名清楚的 preset:

```text
信息可见性
  independent | sequential

议程推进
  fixed_round | issue_driven

讨论动作
  claim | challenge | respond | revise | reinforce | broaden

最终读出
  chair_synthesis | issue_review | independent_attestation
```

这些维度不应重新混成一个 `protocol` 字符串。`until_consensus` 是停机条件,
`gate_each_round` 是人类控制点,二者也都不是讨论范式。

建议产品入口先保持三个:

| Preset | 适用场景 | 核心流程 | 默认态度 |
|---|---|---|---|
| **圆桌会诊** | 开放性判断、方案讨论 | 独立开场 → 共享讨论 → 综合 → 签注 | 默认 |
| **定向质询** | 已有明确分歧且需要收口 | 独立开场 → 台账选靶 → 质疑/回应 → 综合 | 按需 |
| **红队评审** | 架构、合同、风险与高影响方案 | 独立初判 → 指定反方挑错 → 回应 → 复核 | 按需 |

“至共识”保留为停机模式,不另造第四套会议模板。正反辩只适合二元命题,
不应成为众神殿默认形态。

## 下一阶段:从“有台账”到“有讨论动作”

### R1 动作与目标贡献(最先做)

在现有 `Contribution` 上增加**可选的讨论动作元数据**,不改写原始陈词:

```text
动作:主张 | 质疑 | 回应 | 修正 | 补强 | 拓宽
目标贡献:<已知贡献 ID,质疑/回应/修正时必填>
被挑战命题:<一句话,必须能定位到目标贡献>
证据句柄:<文件、命令、贡献 ID 或明确标为未核验>
回应结论:<接受 | 部分接受 | 拒绝,仅回应时必填>
```

规则:

- 默认圆桌会诊不强制每席每轮都有结构化动作;它不能让普通发言失效。
- 定向质询中,每席每轮最多一个主要质疑,质疑必须指向一个具体主张。
- 未知目标 ID、空目标或无法定位的命题不进入关系图;保留原文并记 warning,
  不能让格式失败吞掉发言。
- “质疑”针对论证、证据、适用条件或验证方法,不针对席位人格。
- 被质疑席下一轮必须明确“接受 / 部分接受 / 拒绝”;拒绝也要给证据或验证路径。
- 同一主张被重复质疑但无新证据时,不新开条目;更新“最后保留轮次”并要求收口。
- 动作以尾部受控行解析,不要求异构 CLI 输出完整 JSON;解析失败降级为普通陈词。

这样可以同时吸收 Captain Claw 的动作与目标机制,又不把自然发言变成脆弱的格式考试。

### R2 从质疑生成或更新分歧条目

现有台账主要由“剩余分歧”行驱动,适合保底,但不够直接。R2 只对**影响推荐**的
质疑建条,避免把错别字、措辞偏好和无限实现接缝都变成阻塞项。

建议关系:

```text
Contribution(claim)
  ← targetContributionId
  ← Issue(question/challenge)
      ├─ evidence
      ├─ flipCondition
      ├─ verification
      ├─ response: accept | partial | reject
      └─ status: open | resolved | dissent
```

归因纪律:

- “异议方”只记实际提出质疑的席位;
- “主张方”只从明确引用的贡献 ID 解析;
- 不把其余所有席位猜成同一阵营;
- 未定位时显示“未定位”,不按措辞相似度强行补位;
- 只有提出者或其明确授权后续发言能撤回自己的异议,主席审阅只能建议;
- 用户插话也进入同一台账,以用户贡献 ID 为证据句柄,不能另建一套“用户意见”账本。

### R3 用 DID 决定是否再开一轮

未闭合分歧本身不是继续讨论的理由。续跑前逐条问:

> 下一轮是否存在一个实际可执行的核验动作,其结果可能改变推荐、适用条件或阻塞状态?

满足任一条件才算 DID:

- 读取一个尚未读取的权威文件或数据源;
- 执行一个只读验证命令并记录结果;
- 取得一个可定位的独立来源;
- 向用户提出一个只能在产品/价值层面回答、Agent 无法自行裁决的问题。

以下不算 DID:

- “继续讨论”“再听听大家意见”;
- 重复同一证据;
- 只换措辞重申立场;
- 永远可以继续补充的通用风险;
- 没有负责人、输入或验收结果的“待验证”。

没有 DID 时:

1. 保留未闭合条目;
2. 进入协作综合;
3. 有阻塞争议则交用户裁决或明确条件;
4. 不追加空转轮次。

这与当前固定轮次与至共识安全上限兼容:固定轮次仍可按时收口;至共识只在
全体有效席位声明一致、剩余分歧为空、且没有运行缺口时提前停止。

#### 2026-11-03 R3 落地记录

- 新增 `preset=roundtable|targeted_challenge`;定向质询强制独立开场,
  至少两位参与者、至少两轮,避免第一轮就被圆桌接力锚定;
- 出题页可显式选择“圆桌会诊 / 定向质询”,纪要摘要同时记录议事形态与信息可见性;
- 用户插话立即生成 `origin=user` 的同源台账条目,正文与贡献 ID 一并入账;
  各席可用 `回应` 动作指向该用户贡献,接受后条目转 `resolved`,部分接受或拒绝继续保留;
- 至共识模式在每轮后计算 DID 指纹。只有未消费、可执行且能改变判断的核验动作
  才允许继续;同一核验重复出现不会续命;
- DID 使用与停止均写事件。停止后进入协作汇总,导出“停止信号”明确写
  “没有新的可执行核验动作(DID)”,不再伪装成达到安全上限;
- 固定轮次模式不被 DID 提前截短;它仍按用户指定轮数执行;
- 尚未落:红队 preset、独立确认、行动清单与用户指定核验负责人。

### R4 签注前独立确认(高保障可选)

只在用户明确选择红队评审/高保障时启用。主文生成后冻结一版:

```text
准备签注的小结
  + 完整分歧台账
  + 缺口与失败席位
  + 证据句柄
```

所有有效席位独立回答:

- **支持**:我愿意按这一版签注;
- **有条件支持**:哪些条件必须写进结论;
- **反对**:反对哪条结论/证据/适用条件,以及什么证据能改变它。

约束:

- 不展示其他席的确认结果,避免从众;
- 不计算团队分数、不评选最佳 Agent、不生成胜率;
- 不把“多数支持”改写成“事实已证实”;
- 存在阻塞异议时,主席最多修订一次,修订前后版本都保留;
- 最终正式结论仍由用户签注,不由 Agent 投票自动生效。

#### 2026-11-03 R4 落地记录

- 新增 `red_team` preset：定向讨论后自动进入独立确认；
- 每个有效席位并行确认冻结小结，不展示其他复核席立场；
- 复核结论为 `support / conditional / oppose` 加理由、条件与相关分歧；
- 只要出现 `oppose`，汇总席最多修订一次；原小结存入
  `verdictRevisions`，最终小结记录 `revisedFromSha256` 与修订理由；
- 独立确认与修订历史进入签注哈希，同样的小结配上不同复核不能签成同一版本;
- UI 在结论区显示复核分布、各席理由、条件、分歧与修订说明;
- 默认圆桌/定向质询不调用复核，避免把所有议题成本抬高。

### R5 行动清单只读,执行另立模式

`Verdict` 可增加行动提案:

```text
action             具体做什么
rationale          为什么现在做
dependsOn          前置行动
acceptanceEvidence 怎样算完成,需要什么证据
suggestedOwner     用户/某类能力席位
risk               失败、越权或不可逆风险
```

行动清单只进入纪要和签注审查,不自动派工、不写盘、不运行有副作用命令。

未来“事工房”必须重新取得授权,并满足:

- 独立工作区与写入范围;
- 目标、依赖、状态、结果与验收证据;
- 每条用户插话进入可见时序;
- 重试幂等,不能重复产生副作用;
- 完成状态不等于结论正确,仍需人工验收。

#### 2026-11-03 R5 落地记录

- `Verdict.proposedActions` 已接入汇总 JSON、JSON 导出与最终 Markdown;
- 每项保存动作、理由、依赖、验收证据、建议负责人与风险;
- 结论区明确标注“行动提案 · 只读”“不会自动运行”;
- 无执行器、无自动派工、无工作区写入，执行仍须未来独立模式和重新授权。

### R6 用离线对照决定哪些模式值得留下

先不继续扩 UI。用 20 至 30 个真实议题做受控对照:

| 对照 | 目的 |
|---|---|
| 单席直答 | 最低成本基线 |
| 独立多答 + 综合 | 检验共享上下文前的集成价值 |
| 独立多答 + 固定投票 | 只用于有离散答案的题,检验多数基线 |
| 当前圆桌会诊 | 当前默认 |
| 定向质询 | 检验“挑战已知分歧”的增量 |
| 定向质询 + 独立确认 | 检验复核是否减少重大遗漏 |

每场固定 Harness/模型版本、工具权限、材料、轮次与超时,记录:

- 用户接受率;
- 事实错误和关键反例发现率;
- 证据覆盖与未核验主张比例;
- 正确少数意见是否保留;
- 阻塞异议是否被提前消失;
- 轮数、耗时、调用成本、截断与缺口;
- 用户是否愿意再次使用。

若定向质询不能在“关键反例发现率”或“用户接受率”上稳定优于圆桌,
却显著增加成本,就不设默认;若确认阶段只能增加形式感,也不进入常规流程。

## 现有 P0 / P1 / P2 的保留与重排

以下三节保留此前四席核验出的机制判断;本次新增 R1-R6 作为协议层的后续刀序。

## P0 真相单源化(其余一切的字段都会记在被覆盖的视图上)

四席用两场实弹+代码链钉死的三层同族病:

1. **席位状态冻结**:seatstate 终态只许自环(单次 attempt 正确),但 Participant 对象
   跨轮复用→第二轮起 running/failed 写不进,Status 永远 finished;Gaps 只读 Status
   →末轮 1/4 席在场仍报「无缺口」,Partial 用累计 successful→false,签注指纹覆盖不到缺席。
   12 轮场实证:58 条状态拒绝 warning,zcode 缺席 11 轮、汇总选了空结果的 zcode。
2. **假门与插话擦除**:五个人类入口(插话/门/问/答/解门)各自 get-copy-save,活循环
   高频保存点秒级擦掉它们;手动 OpenGate 改磁盘副本活循环看不见;ResolveGate 无活跑
   守卫+cancel 覆盖→**双活循环并发写同一会话**(zcode r6 静态推演,守卫缺失是代码事实)。
3. **修法共识(zcode r6 e + grok r8 b + codex r9 a)**:
   - 事件投影纯函数:按 CallID 重放 agent_started/output/error/skipped 现算
     started/succeeded/failed/skipped/not-started,签注时必填,不落第二份字段;
   - 挂账队列+交付收据:五入口只投队列,run 循环在停车点 drain 进 history,每个贡献
     ID 记交付收据;结案门=收据覆盖全部挂账,未消费插话 ID 进签注哈希;
   - 轮边界具名控制动作(OriginLauncher+抬 Incarnation),不放宽转移表、不复用
     rebindSeatLocked(那是 OriginUser 通道,grok r8/codex r9 双确认);
   - 前置:session.json 单写者+版本检查持久化(原子写只防半截 JSON,不防旧对象
     覆盖新事件——codex r9)。

## P1 收口机制改造(治「永不收口/收口失真」)

1. **分歧台账**:按分歧点(非席位)记账 `{issue_id, 主张方, 异议方, 证据句柄, 翻转条件,
   状态, 是否阻塞, 下一步核验, 去向}`(codex r9 b 收窄为「只影响推荐的主张」,不全量);
   每轮注入、逐条闭合、默认保留开放项,不因汇总没复述就消失;用户插话进同一账本。
   - **2026-11-03 续落地**:固定轮次也解析分歧；台账已保存主张方/异议方、
     证据句柄、翻转条件、下一步核验、阻塞状态、撤回依据与最终去向。主席 JSON
     已按 `issueId` 输出逐条审阅，遗漏/重复/未知 ID 留运行警示；审阅不覆盖
     提出者撤回状态。用户插话进入同一账本仍待后续。
2. **翻转举证**:共识信号翻转必须附「被哪条证据说服」,否则记 conformity 不算共识
   进展(外部:Not All Flips Are Conformity 等,多 agent 翻转多是从众)。
3. **停机判据**:「剩余分歧≠无」进停机条件(现 consensusMarker 只认共识行,「自报一致+
   正文藏分歧」可同时成立且测试已固化为预期——grok r2 实测);继续/停止由「有无下一轮
   实际减少不确定性的核验动作(DID)」决定,dsh r4:unresolved 是主张状态不是续跑决策。
   - **2026-11-03 续状态**:“剩余分歧非空则阻止全员一致提前停机”和
     “至共识模式无新 DID 则不再追加空转轮次”均已在工作树实现;固定轮次仍按用户
     指定轮数执行。DID 使用与停止都进事件和导出,恢复时从事件重建已消费指纹。
4. **收口检查并行隔离**(grok r4):末轮问「若现在签注你是否会签」而非「是否同意」,
   复用第 1 轮并行隔离形态——逼出「方向同意但这条不敢签」的保留。
   - 当前尚未落成独立确认阶段;归入 R4,且在离线评测前不默认开启。

## P2 协议形态(外部证据驱动)

- 默认基线=独立开场(已落)+集成;完整辩论轮(第 2 轮起)按需启用,须证明增量价值;
- 定向质证先作为现有 `discussion` 阶段内的动作能力落地,只攻证据、不重申立场;
  `PhaseChallenge` 只是历史兼容标签,在状态机、事件、UI 与恢复语义全部定义前不得复活;
- 匿名化与席位实名产品语言冲突(zcode r1 引 Delphi/身份偏见研究),挂权衡不做默认。

## 已销项(2026-11-03 五刀,不重复立项)

插话复读回归/主席轮间小结/共识三行制遗留台账/汇总提炼式/转述纪律三级证据/质量阶梯;
zcode 空结果(4MB cap)已根修——席位失败率主因已除,冻结链的「缺席」数据将大幅干净。

## 明确不抄

1. 不暴露 144 种 MALLM 式配置;可组合性留给评测与内部模型。
2. 不让模型自评 suitability 决定默认发言权。
3. 不把陪审团变成 Agent 排行榜,不把关键词匹配分数当逻辑质量。
4. 不用未校准 confidence 冒充事实可信度。
5. 不把多数投票或“赢了一场辩论”当成命题为真。
6. 不在议事阶段自动写盘、运行副作用命令或派工。
7. 不为桌面单机引入 Matrix/Kubernetes/MinIO 全套执行基础设施。
8. 不把多轮讨论默认视为更强;先与单席、独立多答、固定投票和当前圆桌对照。
9. 不为结构化字段牺牲有效发言:解析失败降级并留痕,不因格式吞掉一次发言。
10. 不建立第二套席位状态、分歧状态或签注真相。

## 验收标准

第一轮协议迭代至少满足:

1. 用户能识别一轮发言是在主张、质疑、回应、修正、补强还是拓宽;
2. 每次质疑都能定位到已知贡献 ID 与具体命题,未定位时如实显示并告警;
3. 被质疑方在下一轮明确接受、部分接受或拒绝,拒绝附证据或验证路径;
4. 分歧台账覆盖“质疑产生”和“剩余分歧”两条入口,用户插话不另建账本;
5. 主席审阅不覆盖提出者的撤回或保留状态,主席也不能静默删除台账条目;
6. 没有 DID 时不继续空转;保留分歧进入综合与用户裁决;
7. 至共识只在全体有效席位一致、无阻塞剩余分歧、无运行缺口时提前停止;
8. 高保障确认保留反对意见与修订前后版本,不产生团队分数或 Agent 排名;
9. 行动清单可查看、导出、采纳或拒绝,但议会不会因此获得写权限;
10. 协议对照记录 Harness/模型版本、权限、轮次、成本、证据覆盖、
    少数意见保留和用户接受率,而不只记录“看起来讨论充分”;
11. 新增实现不破坏当前 `pantheon-issue-ledger`、轮次、插话、决策门、
    取消恢复和签注指纹契约;
12. 若真实议题对照未证明增益,产品文案退回“多 Agent 会诊”,不宣称辩论提高正确率。

## 施工顺序

前置事实:当前工作树已有 P0 的 Attempt/观测/恢复/缺口链,以及 P1 的分歧台账、
主席逐条审阅和“剩余分歧阻止假共识”。这些先稳定、测试和验收,不在其上再建平行结构。

```text
稳定 P0 真相单源
  → 稳定 P1 台账与决策门交付
  → R1 动作与目标贡献
  → R2 质疑生成/更新台账
  → R3 DID 停机与用户裁决
  → R6 小规模离线对照
  → 依据对照结果决定 R4/R5 的默认曝光
  → 签注后的独立“事工房”另立项目
```

说明:R4/R5 的机制契约已提前落地为高保障可选能力;在 R6 完成前，红队评审
保持显式选择，不进入默认流程，行动提案也不获得执行权限。

不建议先做 UI 大改、正反辩模板或陪审团排行。评价面板和协议选择器应在后端语义、
事件一致性、恢复语义与对照结果稳定后再加。

## 研究边界

- MALLM、Captain Claw、ARTEMIS、AgentTeams 的核验是源码与公开文档层面的
  机制核验,不是对四个项目做独立效果复测。
- MALLM 的论文结果不能直接外推到 Codex/ZCode/DSH/Grok 异构席位;工具权限、
  模型版本和 Harness 提示差异会混入处理效应。
- Captain Claw 的议事交互成熟,但没有找到与本项目同任务、同模型、同权限的受控评估。
- ARTEMIS 的评分与自测口径不足以作为事实权威;只借职责分离与异议保留。
- AgentTeams 的任务执行设计成熟,但部署面和权限模型明显重于当前桌面只读议事。
- 众神殿的最终取舍必须来自本机真实议题对照,不能因上游 star、功能数量或
  “多 Agent”标签自动获得授权。

## 最终判断

众神殿下一轮迭代不是“把四个辩论框架搬进来”,而是把现有圆桌从**自然语言讨论记录**
升级成**可定位的论证过程**:

1. 每轮能看出讨论动作与目标论证;
2. 每条关键异议有证据、翻转条件和核验路径;
3. 没有可减少不确定性的动作时,及时收口;
4. 结论可独立复核,少数意见不会被投票或综合吞掉;
5. 行动只作为签注后的提案,执行仍受独立授权约束。

先完成 R1-R3,再以真实议题对照决定是否开放 R4、R5 和更多协议形态。
