# MCP 双向枢纽翻案评估（拍板池条2 · 2026-09-13）

> 成 server,入=管家挂外部工具;翻案=按治理规则激活重议)」。

| 方向 | 状态 | 证据 |

## 2. 「出」方向的价值假设与检验

**假设**:在外部 AI 客户端(Claude Desktop/Cursor 等)里直接查 gaea 的造价库/
记忆/办公文档。

**检验**:
1. **与自身入口重复**:同样的能力(造价检索/AI 组价/记忆问答/办公编辑)gaea
   界面里都有,且带证据链与确认流;外部客户端只能拿到「裸工具调用」,丢失
   gaea 的治理层(hardAsk 确认/留痕/审批分级)。价值=「换个客户端用同一批
   数据」,属边际便利。
2. **工程形态矛盾(最大反对证据)**:gaea 是 Wails GUI 单体,数据在用户目录
   SQLite。暴露为 MCP server 只有两条路:
   - **壳内嵌**:壳关即断——外部客户端依赖 gaea 常驻运行,「个人常驻管家」
     的实际使用模式(随开随用)下可用性差;
   - **独立 server 进程**:跨进程生命周期管理+同一 SQLite 的跨进程写并发+
     版本漂移(两份可执行),把单体应用的简单性永久拆掉——这正是「平台化」
     排除史要防的结构性滑梯。
3. **安全暴露面**:个人记忆/办公文档/造价数据经第三方客户端的工具调用读取,
   审批与留痕治理不在 gaea 掌控内;与「本机管家一切留痕」人设张力大(同
   壳外 computer use 的否决理由)。
4. **窗口论修正**:「事实标准已成」确实(2026 MCP 广泛采纳),但**窗口收窄
   不构成做它的理由**——gaea 的定位是本机私人应用,不是被集成的平台;错过
   「被集成窗口」没有损失,错过「私人助手体验」才有。

## 3. 建议

**维持排除,翻案不成立**。核心理由:出方向的工程形态矛盾不可调和(GUI 壳 vs
常驻 server),价值假设与自身入口重复,安全暴露面与人设冲突——三条独立理由
同向,且与在册排除的原始治理逻辑一致。

若未来确有外部集成需求,届时更轻的替代是**单向导出**(如记忆/指标的只读快照
文件)而非常驻 server——留作观察,不立项。

## 4. 拍板选项

1. **维持排除**(建议):拍板池条2 移除,本文档为评估依据;「入」方向照常演进。
2. **试点最小出方向**:仅壳内嵌只读 server(cost search/memory search 两个
