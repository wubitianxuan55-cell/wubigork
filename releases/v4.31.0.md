## 交付明细

### ① 产物版本时间线·单版本入口（线 A，收 v4.28 B1 欠账）

- **问题**：产物行的 vN 版本徽标只在 `versions > 1` 时渲染——「会话内只出现 1 次的产物」没有
  版本时间线入口，即使该文件在证据链 JournalList 里有带 baselinePath 的写盘快照，也无法点开
  逐版本列表/预览/恢复。
- **修复**：徽标渲染条件从 `{rev && …}` 放宽为 `{(rev || journalEntry) && …}`——`versions > 1`
  完全按现状渲染 `v{N}` 次数徽标（title/文案原样，旧锁不破）；`versions ≤ 1` 但该路径在
  journal 分组（`groupVersionsByPath` 只留有 baselinePath 的卡）存在条目时，渲染「版本」入口
  徽标（Rollback 图标 + primary 色胶囊同款），title「有版本历史（可预览/恢复）」区分语义；
  无快照记录不渲染（保持空态）。VersionTimeline 本体零改动（单条/空态/加载态已支持）。
- 测试：DeliverablesPanel.test 30→33（+3：versions=1 有快照渲染入口并展开/预览/恢复可用；
  versions 省略有快照同样渲染；有快照行 + 无快照行同面板对照仅 1 个入口）。

### ③ 轨迹/对话历史轮耗时（线 C，收 v4.26 欠账）

- **问题**：WorkHeader「已完成 · 用时 · N 步」只对当前轮 running 态有时钟；历史轮（读盘折叠
  出来）无耗时数据源——轨迹轮次头看不到每轮花了多久。
- **修复**：后端 `Turn.DurationMs int64 \`json:"durationMs,omitempty"\``（与 Record.DurationMs
  命名/换算对齐）——fold.go turn_done 分支 `if e.Ts > f.cur.StartedAt { DurationMs = (e.Ts −
  StartedAt) × 1000 }`，悬挂轮/时钟异常保持 0（omitempty 省略，旧日志/旧后端向后兼容）。
  前端 `TrajectoryTurn.durationMs` 同步；TrajectoryView 轮次头在 `turn.end && durationMs` 时
  显示「用时 Ns」（复用 v4.26 formatElapsed：<60s「30s」/≥60s「1m40s」），running 轮不显示。
  **零新增绑定**：GaeaTrajectory 直接返回 struct，字段级无需重生成。
- 测试：Go +2（duration 计算/omitempty 序列化，golden 逐字节不变）；前端 +3（<60s/≥60s/无
  end 或无字段不显示）。
- 说明：WorkHeader 消费历史轮耗时（任务 b）不可行——WorkHeader 只吃实时 store，无 trajectory
  数据；历史轮只存在于 TrajectoryView 的拉取快照，消费需新增数据源接线，超出本刀范围。已跳过。

### ④ TestCancelConcurrentStress flaky 根治（线 D，沿旧欠账）——**实现层真竞态**

- **根因（非计时 flaky，是实现语义竞态）**：`pickNext` 无 PerSpace/Priority 时裸读
  GetFirstQueued 不做任务级预留 → 同一 queued 任务可被多个 worker 同时 execute()；每个 worker
  claim 前预注册 `m.cancels[id]`（落选者覆盖胜者）；**claim 落选者的 `!claimed` 分支无条件调
  unregisterCancel 删除 cancels + cancelReq（用户取消意图）**；Cancel 已按 running 分支成功返回
  （fire 的是落选者残留 ctx，胜者 ctx 未中断）→ 胜者收尾读 userCancel=false → markTerminal
  (Succeeded) 覆盖 stopping——`Cancel()==nil` 但终态 succeeded，违背 v4.8.2 回归锁。单包
  `-count=30` 第 21 次失败、探针轨迹恒为 `[queued running stopping succeeded]` 实锤。
- **修复**（tasks.go 最小，+42 行）：`!claimed` 与 claim 错误分支改用新 `clearStaleCancel`
  （只清理确属残留的预注册、**绝不删 cancelReq**——用户取消意图归胜者 worker 消费）；claim
  成功后**胜者重新登记自己的 cancel** 覆盖落选者预注册（Cancel 命中真正执行 handler 的 ctx）；
  clearStaleCancel 在 m.mu 下查状态（仍 running/stopping 归胜者不动，终态/queued 才删残留防
  泄漏）。测试无法独自修复（断言是回归锁不得削弱，计时改法治不了 50ms 内语义失败），故最小
  改动实现。
- **测试**（tasks_test.go +118/-20）：等待改**事件驱动**（markTerminal 落库后同步 emit，50 个
  终态事件到齐即终态，30s 兜底替代固定 10s 轮询）；断言不削弱且**双向加固**——「Cancel()==nil
  ⇒ 终态 cancelled」（v4.8.2 回归锁原样保留）+「未取消 ⇒ 终态 succeeded」（handler 的 ctx 仅由
  Cancel 成功路径取消，修复后确定性成立）+ 终态事件不重不漏（每任务恰好一个终态事件）+「至少
  一个 Cancel 成功」防空转；另新增确定性契约单测 **TestClearStaleCancelOwnership**
  （running/stopping 保留注册、终态清残留、任何情况不删 cancelReq——不依赖压力命中的概率窗口）。
- **验证**：`-count=20` 全绿、`-count=100` **两轮**全绿（修复后 + 断言加固后各一轮）、tasks 包
  `-count=3` 全绿、全量 Go **0 FAIL**（修复前后各跑一次）。`-count=2 ./...` 仅既有 -count>1
  问题（billing/boot/provider duplicate kind 全局注册表、whisper 10m 超时）——billing/boot/
  provider/whisper 均不 import tasks；internal/app 虽 import tasks，其失败为全局注册表
  duplicate kind，`git stash` 复跑结果一致，证明均非本改动引入。
