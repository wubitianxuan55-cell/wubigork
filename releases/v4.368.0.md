# v4.368.0 — 性能轮深水区：聊天流式分段渲染（O(n²) 根修）

> 用户口径「继续」——性能留池最大的一项落地：聊天流式回复时每个 delta chunk 都对**全量累积文本**重新跑 react-markdown 解析（remarkGfm+remarkMath+rehypeKatex），O(n²)——5KB 尾段单次 parse 5~20ms × 30+ chunk/s = 主线程持续高占用与 GC 压力。本轮移植 gaea 侧已验证的「稳定分段」设计到聊天流式行，每 chunk 实际重解析的只有增长中的尾段（通常一段）。前端 3 源文件 + 1 新测试，绑定面 706 不动。

## 方案（三选一后定为方案A：ChatRow 流式分支分段）

调研对比：方案B（MarkdownContent 内部分段，对所有消费方透明）会冲击 `MarkdownContent.t74.test.tsx` 精确的 ReactMarkdown 调用计数断言、且波及非流式消费方（NovelSettingPage 预览/角色终态）——不选；限频兜底（把 rAF 换 50~80ms 节流）只降频率不降单次 parse 规模——不作主案。**方案A 影响面锁死在 ChatRow 流式分支，非流式路径逐字节不变。**

## 落地

1. **findStableCut 导出 + 盲区修复**（gaea/components/MemoMarkdown.tsx）——切分规则：在最后一个空行（`\n\n`）处切，稳定段之前；**顺手修了 gaea 侧一直存在的盲区**：原实现只扫切点之后的 suffix 判断 fence 状态，fence body 含空行（代码里极常见）时计数为偶数误判「可切」，把代码块拦腰切断（稳定段含悬挂 fence、尾段代码行被当正文渲染的瞬时错排）。改为全量行扫描候选切点之前的行首 ``` 标记：切点落在未闭合 fence 内则回退切点到该 fence 打开行之前（切分只会更保守，稳定段永不含悬挂 fence）。既有 MemoMarkdown 测试零改动通过。
2. **ChatRow 流式分支两段渲染**：`useMemo(() => findStableCut(display), [display])` → `<MarkdownContent source={stablePart}/>` + `<MarkdownContent source={pendingPart}/>`。stable 段字符串在跨过新段落边界前不变 → 其 react-markdown 子树被 memo 整体跳过；pending 段（通常 KB 级）每帧重解析。终态（streaming 翻转）回到既有全量渲染路径，零变化。

## 契约与兼容

- **genui 契约零破坏**：分段函数把 genui fence 当普通 fence（闭合 fence 完整落稳定段）；流式分支本就不传 genui overrides（流式中 genui 显示为原始 JSON 面板、流结束变组件——现状不变）。ChatMarkdown.genui.test.tsx 全绿。
- **已知接受的瞬时折衷**（与 gaea 同款）：松散列表（列表项间空行）在流式中序号可能短暂重排，终态自愈；streaming 翻转瞬间 stable+pending 两块合并为单块，DOM 重建一次。
- 相比 gaea 原设计的改进：聊天侧尾段走完整 react-markdown 管线（非行级仿制 HTML），未闭合 fence 在流式中显示为持续增长的代码块，更接近终态。

## 坑

1. **正则整段替换函数体时非贪婪匹配会吞闭合括号**——`.*?\n\}` 匹配到函数内第一个顶格 `}` 之前是对的，但替换串本身忘了带 `}`；替换后立即 tsc（ Unterminated/缺 `}`）当场暴露。
2. **性能改造的行为等价是「终态等价」**——流式中间态的 DOM 结构从单块变两块（stable+pending），终态渲染路径不变；这类优化验收口径=终态一致+中间态不劣化，不能拿中间态 DOM 逐字节比。
