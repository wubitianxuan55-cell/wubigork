## 刀B：并发加固 4 刀（观察池 → 根修）

5. **PrepareContinue TOCTOU 根修**（`internal/gaea/agent/subagent_store.go`）：meta.Status 非 running 检查与 MarkRunning 写回之间有窗口，双路续跑同 ref 交错写转录——绑定层 followUpClaims 只盖 UI 路径，TaskTool continue_from 工具路径无守卫。修法=**接通 store 里的半成品**：`SubagentRun.release` 字段与 `Release()` 调用（所有调用点本就有 defer）三件齐备但 store 从不赋值（恒 no-op）。store 加 `continueClaims sync.Map`：PrepareContinue 校验通过后 LoadOrStore 占 ref（第二路报 "already being continued"），claim 随 `run.Release()`（调用方 defer）或终态写（SaveCompleted/SaveFailed 兜底 Delete，防忘 Release）释放；转录 Load 失败路径不占坑。绑定层 claims 保留（受理前置快速拒绝），零调用方改动。
6. **cost BM25 语料/版本戳原子化**（`internal/gaea/cost/cost.go`）：rankerFor 内部再 Load 版本与调用方 SQL 捞语料非同一时点——写路径在两步之间推进版本，旧语料挂到新版本 key 上一直用到下次写。修法=调用方捞语料前快照 `corpusVer := rankVersion.Load()` 传入 rankerFor（签名加 version 参数），语料与版本戳原子。
7. **weixin Stop→Start 双轮询根修**（`internal/channels/weixin/clawbot.go`）：旧 pollLoop 可能还睡在轮询间隔/长轮询 HTTP 里，Stop 后立刻 Start 时 running 被 Swap(true) 复位——旧 loop 醒来循环条件复活，与新 loop 并行双轮询。修法=生命周期代际 `gen atomic.Int64`：每次 Start 递增，pollLoop 捕获启动代，`alive() = running && gen==启动代`；panic 兜底的 running 复位同样加代际守卫（防旧 loop panic 把新 loop 误打掉）。
8. **realtime Dial 双拨号泄首连**（`internal/realtime/openai.go`）：检查（conn==nil）与赋值之间有窗口——并发双 Dial 输家直接覆盖 s.conn，赢家连接被遗忘且无人 Close（fd 泄漏 + 双 readLoop）。修法=CAS 落位：锁内重检 closed/conn，输家关掉自己拨到的连接再报 already connected / session closed。

## 坑

1. **半成品机制比没有更危险**——release 字段+Release() 调用+注释三件齐备却无人赋值，读代码会误以为守卫存在。新并发守卫落地后第一步 grep 赋值点验证接线完整性。
2. **可见化 ≠ fail-closed**——幂等写失败（dag sweep/状态标签）warn 即可不阻断主流程；判据=失败是否改变主操作结果。版本本体已落库而标签写失败时，报错返回反而制造假失败。
3. **代际修复要同时护 panic 兜底的复位路径**——pollLoop 的 running.Store(false) 若不带代际守卫，旧 loop 的 panic 会把换代后的新 loop 误打掉（IsRunning 误报）。
4. **吞错修复优先改签名上抛而非原地打日志**——ListChatEnabled 式「返回零值+吞 err」让所有调用方共享失明；签名改动是编译器强制的全调用点审查。
