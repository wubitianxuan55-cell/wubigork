## 落地

- **三个清理入口（新 `internal/app/foreshadow_cleanup_handler.go`，spec §8.1，语义严格区分）**：
  - `DeleteChapterForeshadows(chapterFile, onlyAnalysisSource)`——章节清空/重新生成：删 `PlantedIn==ch ∨ RevealedIn==ch`；`onlyAnalysisSource=true`（默认语义）只删分析来源，手动条目永不被批量删除（关键不变量：source_type 是批量清理唯一判据；存量无 source_type 的条目按手动保护）。
  - `CleanChapterAnalysisForeshadows(chapterFile)`——**重新分析前**：①只删「分析来源 ∧ 埋入本章」（重分析可再生）；②回退本章回收条目（`RevealedIn==ch ∧ status ∈ {revealed, partially_resolved}` → planted，清空 RevealedIn/ResolvedAt/ResolutionText）——§8.2 允许的系统内部迁移，不暴露其他 API。
  - `ClearProjectForeshadowsForReset()`——全新生成/项目重置：删全部分析来源；手动条目**重置不删除**（→pending，清空 PlantedIn/RevealedIn/TargetResolveIn/PlantedAt/ResolvedAt，标题/描述/长线标记保留）。
  - 统一返回 `ForeshadowCleanupResult{deleted, rolledBack?, resetManual?}`（wire camelCase，形状锁覆盖）；登记表缺失=无事可清正常态；写回走原子写。
- **统计口径（`GetForeshadowStats(currentChapter)`，spec §5.1）**：`ForeshadowStatsReport{total, pending, planted, hinted, resolved, partiallyResolved, abandoned, longTermCount, overdueCount, currentChapter?}`——`resolved` 别名读取归一并入（`NormalizeForeshadowStatus` 唯一入口）；`overdueCount` 只在当前章 >0 时算，存活条目（planted/hinted/partial，D15 口径）×`ClassifyResolve==overdue`（分层/超期判定全仓唯 types 一处，D9 延续）；`currentChapter<=0` 自动按已写章节数；Total=分桶之和（未知状态不入桶，交 Lint/校验面暴露不猜）。
- **Lint 扩两码（`novel_foreshadow_lint_handler.go`，spec P3.4，5→7 类）**：
  - ⑥ `overdue`（medium）：存活 ∧ 计划回收章 < 已写章数——超期条目会以硬约束进生成上下文（v4.293 调度注入），作者应尽早处置。
  - ⑦ `unplanned`（low）：存活 ∧ 未填 `target_resolve_in` ∧ 已埋入 ≥10 章（长线豁免，与 stale 同理）——与 stale 的差异：stale 说「该收了」，unplanned 说「缺计划字段，无法参与按章调度」，建议动作不同，两码并存。
  - 既有五类检查零改动（既有测试原样通过）。
- **gaea 适配（有意偏离，码内注明）**：不引入 `SourceAnalysis` 引用匹配分支（gaea 同步层从不写该字段——引入即 MuMu D5 死代码同款）；§8.3 单条删除联动依赖「持久化分析记录」，gaea 分析产物不落盘无联动目标，暂不做（分析记录若日持久化再补）。
