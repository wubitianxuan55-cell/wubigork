# v4.63.2「并行子代理：同回合批量派发不再串行排队」

> 发布日期：2026-09-04 ｜ tag：`v4.63.2` ｜ 基线：v4.63.1 ｜ 绑定面 **559
> 零变更** ｜ 用户实测发现：三个测试子代理是串行执行而非并行。

## 根因（实锤）

会话账本显示 3 条 task 派发**同一秒**落账（模型确实一次批量发了 3 个并行
调用），但三个 sa_ 运行的创建时间是 09:50:13 / 09:54:21 / 09:58:57——各自
在上一个完成后才启动。串行点在执行器分区器：getConflictKey 把
task/run_skill 归为**全局冲突键 "!spawn"**（v4.61 入口收敛时与
install_skill 合并归类），分区器对全局冲突键一律「单调用串行批」→ 同回合
N 路派发逐个排队。

## 修复

- **task / run_skill 改「每调用唯一键」spawn:<callID>**：N 路派发全部落进
  同一并行批（runParallel 上限 8 并发，panic recover 兜底）；ID 缺失时退化
  共享键按冲突串行（宁慢勿错）。install_skill 写技能目录保持串行。
- **并行安全配套**：TaskTool 用量记账从「整值覆写（最后一次运行赢）」改为
  usageMu 互斥合并——并行时覆写会丢其他路用量，且指针写本身是数据竞争。
- 并行安全性依据：每次 task 调用独立 Session / 独立 sa_ transcript /
  独立 subReg；子代理事件经 syncSink 串行落主账本；v4.26 的
  SubagentMessage.ParentToolID 与 FE 任务卡 (ref,args) 匹配本就为并行多卡
  设计。

## 如实说明（性能预期）

- 云端引擎：三路真实并行，墙钟 ≈ 最慢一路。
- 本地模型（如 herdsman 单卡推理）：LLM 推理在模型服务端仍可能逐请求排队，
  但三路的工具执行段（web_search / knowledge_search / 读文件等非推理段）
  真实重叠，整体墙钟仍显著小于串行。
