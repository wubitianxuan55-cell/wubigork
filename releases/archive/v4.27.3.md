# v4.27.3「markdown 包裹符 · 交付卡片路径修复」

> 发布日期：2026-09-01 ｜ tag：`v4.27.3` ｜ 基线：v4.27.2 ｜ 绑定面 550 → 550（零变更）

## 问题（真实会话现场实证）

用户报告：**「最后生成的交付卡片点击无法打开，点击文件按钮打开的不是文件位置」**。
主代理在运行中的真实会话（安全文明手册交付）现场观察实锤：

- 交付卡片渲染出来了，但提取到的路径是
  **`` `安全文明手册/双流黄甲金具厂地块土壤污染修复项目安全文明施工标准化手册.docx ``**——
  开头带着 markdown 反引号；
- 点卡片 → `GaeaPreview` 拼出「工作区根 + \`安全文明手册\…」不存在的路径 →
  右栏预览「**文件不存在**」错误卡；
- 「在文件管理器中定位」→ `explorer /select,` 同样坏路径 → 打开的位置不对。

## 根因

`lib/fileLinks.ts` 的路径字符集（PATH_BODY/FIRST_SEG）不排除 markdown 包裹符
反引号 `` ` `` 与星号 `*`——模型用 `` `路径` `` 或 `*路径*` 写文件引用时，
匹配从包裹符开始，把开头反引号吞进路径。这两个字符恰好是 **Windows 文件名
非法字符**，本就应当作路径边界处理（v4.26.1 修全角括号时的同类盲区第二弹）。

## 修复

1. `PATH_BODY` / `FIRST_SEG` 排除集加 `` ` `` 与 `*`（路径体/首段不再吞包裹符）。
2. `PATH_BOUNDARY` 加 `` ` `` 与 `*`（包裹符后的字符是合法路径起点）。
3. `BARE_FILE_RE` 分隔符后允许包裹符前缀（「输出文件：\`报告.docx\`」）。
4. 下划线不受影响（`my_file_name.docx` 仍正常匹配——`_` 是合法文件名字符）。
5. 点击/定位链路零改动：路径干净后 `resolvePreviewPath` 既有逻辑直接工作。

**存量消息自动受益**：卡片路径在渲染时从正文实时提取，应用重启后历史消息
里的旧卡片即恢复可点，无需重跑模型。

## 测试

fileLinks +5：反引号包裹相对路径（真实会话文件名）、反引号包裹绝对路径、
星号强调包裹、关键词引导裸名带反引号、下划线文件名不受影响。

## 验证

tsc -b 0；eslint 0；vitest 1095/1095（169 文件，+5）；Go 无改动；drift PASS
（550）；版本四处 4.27.3。

## 教训

路径类正则的字符集要以「目标平台文件名的合法字符集」为准——非法字符
（Windows: `` \ / : * ? " < > | ``）必然是 markdown/包裹符，应作边界而非路径体。
v4.26.1（全角括号）与本次（反引号/星号）是同一盲区的两连发，本次已把
Windows 非法字符集逐一核对（其余成员早已在排除集内）。
