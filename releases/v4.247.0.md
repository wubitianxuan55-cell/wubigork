# v4.247.0 — 后端性能刀D：cost 检索固定成本（BM25 缓存+客户端单例+子查询消除）（2026-09-12）

## 为什么是这一刀

普查档刀D：cost_search 是测算/组价的高频工具调用，三项固定成本——
每查询对命中子集从零重建 BM25 倒排（2000 条库 20.6ms/22MB 分配）、
每次调用新建 Embedder/Reranker（探测缓存永不命中、keep-alive 全失效）、
逐行相关子查询 COUNT 组件明细。均先立 benchmark 基线再动刀。

## 修复

1. **BM25 排序缓存**（普查#3，T7-3 原设计接通）：刀法修正——bm25.Cache
   原设计语料=整库，而 Search 现行为=关键词命中子集排序，直接接通会改
   BM25 统计口径。改为包级缓存：key = db 池+数据版本+category|status 过滤
   形态，语料 = 该过滤形态下 SQL 全捞全量（name 序）；命中子集按语料下标
   取分，tie-break=语料序（=name 序，与改前一致），TestCostSearchBM25Order
   原样通过。失效全链：Save/Delete/SaveCategory/DeleteCategory 成功推进
   版本 + SelfHeal 实际修复推进 + app 批量导入（直写 UPSERT 不经
   Store.Save）走新导出的 cost.InvalidateRankers 显式失效；map 超 16 项
   整体清空。
2. **Embedder/Reranker 单例化**（普查#4）：按注入的 retrievalRuntime 配置
   为键缓存实例；SetRetrievalRuntime 变更自动重建；构造失败不缓存（下次
   调用重试）；override 测试注入路径不动。60 秒 Available() 探测缓存从此
   真正命中，HTTP keep-alive 复用。
3. **子查询消除**：逐行相关子查询 `(SELECT COUNT(*) FROM
   cost_entry_components ...)` 改 LEFT JOIN (GROUP BY) 单趟扫描；
   ComponentCount 语义不变（COALESCE 0=无明细）。
