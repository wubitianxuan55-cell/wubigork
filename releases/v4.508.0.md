# v4.508.0 · 文件交互四修：PickFiles 选图 type 判空根修+识图不清草稿+base64 分块+附件去重（2026-10-20）

> 用户提「文件交互功能」。2026-08-16 文件交互调研九项池（P0×3/P1×3/P2×3）
> 已全部落地的前提下，代码级走查 Composer 附件链抓出四处实弹病灶。

## ① PickFiles 选图全被当普通文件（主病灶，bug）

`FilePickResult`（Go 契约）只有 `path/name/size`，**没有 MIME `type` 字段**——
`useComposerAttachments.handlePickFiles` 里 `f.type === "image"` 对系统对话框
路径恒 false。用户面：「选择文件」按钮选的图片全部按普通文件处理——无缩略图、
无识图/OCR 入口。拖拽/粘贴路径正常（浏览器 `File.type` MIME 在），所以只在
对话框路径上翻车；`pickFile.test.ts` 的 stub 自己造了 `type: 'image'` 字段，
掩盖了契约现场，bug 得以长期存活。

修：`isImagePath()` 扩展名判断单源（`pickFile.ts` 导出，与
`pickImageAsDataUrl` 白名单同源）。对话框路径统一走它；拖拽路径维持
`File.type` 判断不变。

## ② 识图/OCR 清掉输入框草稿

`handleRecognize`/`handleOCRText` 发送识别结果前 `setText("")`——用户贴图后
先写半句要求再点识图的场景，半句话被整段清掉。识别结果独立成一条消息发送，
草稿保留。

## ③ 非图片附件逐字节 base64（大文件卡 UI）

`for (i) bin += String.fromCharCode(bytes[i])`：10MB 文件 = 千万次字符串
拼接 + 一条 10MB 巨串进 `btoa`，UI 卡秒级。改 `bytesToBase64` 8KB 分块编码，
行为等价（btoa 对 Latin-1 逐字节语义分块无感）。

## ④ 附件无去重

同一文件拖两次/选两次 = 双 chip、提交时同一 `@路径` 注入两遍白占上下文。
三入口统一 `appendUnique` 按 path 去重。
