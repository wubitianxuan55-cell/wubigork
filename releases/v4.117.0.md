## 一、设计立场：引擎裁决，不自动改排程

「倒排」有两种做法：自动把全部任务锁死到倒推时刻（激进），或只设约束、由引擎裁决可行性并给出压缩对象（稳健）。本刀取后者：

- **自动锁死被明确拒绝**——全量 manual 违背手动任务语义（manual 不参与关键线路、不回传约束），会把计划变成死的；
- 压缩方案属于「AI 产建议、用户拍板」：引擎只裁决「目标可达不可达、差多少、压哪些（关键链）」，怎么压由模型建议、用户确认。

## 二、数据模型与口径（双侧同构）

`SchedProject.deadline: string`（YYYY-MM-DD **日历日期**）——存日期而非工作日数：合同竣工日期是日历事实，用户日后调整开工日期时语义稳定（目标工作日数随开工日重算）。

| 字段 | 含义 |
| --- | --- |
| targetWorkdays | 目标总工期（工作日，1-based「第 N 个工作日竣工」）= [开工日, 竣工日] 内工作日计数 |
| feasible | 当前总工期 ≤ targetWorkdays |
| overrun | 超期量：正=超期工作日，负=富余，0=压线达成 |
| criticalTasks | 关键工作名清单（手动不计）——超期时的压缩对象 |

边界口径：竣工日恰为非工作日 → 自然回落到此前最近工作日（计数即「到上一工作日为止」）；竣工早于开工 → targetWorkdays=0，必然不可达（analyze 诚实报告，不静默）。

## 三、引擎（TS 9 例 + Go 9 例镜像）

- calendar.deadlineWorkdays / DeadlineWorkdays：工作日计数（节假日命中不计；周六竣工回落周五）。
- checkDeadline / CheckDeadline：未设 deadline 或计划未通过 CPM → null。
- ops set_meta{deadline}：**指针三态**（nil=不动 / 空串=清除 / 日期=设置）；格式（长度≠10）拒绝；Validate 同步守落盘。
- store.normalizeProject 对 localStorage 旧数据的非法格式 deadline 防御性丢弃。

## 四、agent 三工具接线

- schedule_get：带 `deadline`。
- schedule_apply：回执带 `deadlineCheck`（可行性+超期/富余量+关键清单）。
- schedule_analyze：输出 `deadlineCheck`；checks 追加倒排发现——不可达：「倒排校核：目标竣工 D（第 N 工作日）不可达——总工期 X 天，超 Z 天；需压缩关键线路」；富余 ≤2 天：「距目标竣工仅剩 W 天富余，关键任务拖延即触线」；富余充足**不出发现**（不噪声化）。
- schedule-edit 技能编制流程第 3 步改写（锚点锁 20→23）：约束场景先 `set_meta{deadline}`，analyze 倒排校核裁决；manual 降级为个别任务定位手段。

## 八、诚实边界

- 「第 N 个工作日竣工」口径与总工期口径天然对齐（总工期 141 天=第 141 个工作日收尾），但**不处理「定额工期为日历天」的换算**——那是拍板池「双工期口径」的范围，本刀不越界。
- 竣工线超出画布时状态栏仍如实报数（横道延伸只保证小幅超出；目标过远时以状态栏为准）。
- mspdi XML 导入导出不携带 deadline/baseline（Project 端互换需求出现时再立项）。
