# 灵犀「文件交付卡片」调研

证据来源：`lingxi.exe` 内嵌提示词模板（`templates/tools/deliver_result.tmpl`、`<delivery_format>` 段）、`desktop-renderer-dist` 前端 bundle、以及本仓库 gaea 现有实现对照。
标记：`[观]`=字符串/代码直接命中，`[推]`=结构推断。

---

## 1. 交付有三种形态，各走各的通道 `[观]`

| 场景 | 信道 | 契约 | 原文证据 |
|---|---|---|---|
| 桌面客户端 | 回复正文 markdown 链接 | `[查看文件名](file:///绝对路径)`；图片 `![描述](file:///绝对路径)` | `<delivery_format>` else 分支 |
| Web / 云会话 | 回复正文 markdown 链接 | `[文件名](sandbox:///绝对路径)`；文件夹末尾加 `/` | `<delivery_format>` `eq .ClientType "web"` 分支 |
| IM（群聊/单聊） | **工具调用** | `deliver_result(ref=绝对路径)`，一次一个文件，多文件多次调用 | `<im_scene>` 第 5 条 |

IM 分支明确写了：**禁止使用 `file:///` 链接，因为用户在 IM 中无法打开** —— 也就是 IM 里没有"本地面板"，必须由服务端把文件推成卡片消息。

## 2. 提示词里写死的三条渲染健壮性规则 `[观]`

原文（web 分支）：

> - 引用工作区文件的 markdown 链接写法：`[文件名](sandbox:///绝对路径)`。链接必须直接输出，**前后不要加反引号**，也不要放进代码块——反引号会被解析成代码片段，导致整条消息渲染错乱。
> - 分享图片时使用图片语法，同样不要加反引号。
> - `sandbox:///` 仅用于当前对话中向用户展示工作区文件，不要将这类链接写入项目文件或记忆。
> - 伪协议仅用于用户可见的 Markdown 链接；调用 file、bash、view_image 等工具时，参数仍使用 environment_context 中的真实绝对路径。

对应 IM 分支：

> - 禁止使用 `file:///` 链接，因为用户在 IM 中无法打开。
> - 生成文件后，**优先使用 deliver_result 工具**交付文件，ref 参数填写文件的**绝对路径**（完整路径，禁止使用相对路径），单次调用只交付一个文件，多文件多次调用。

还有一条交付时序规则：**交付阶段的 `c_text` 必须一次性写完整，写完后再调用工具**——因为工具调用会立即中断文字输出，先调工具会让用户只看到半截说明。

## 3. 前端如何把链接变成可打开的文件 `[观]`

`localSessionLifecycle-*.js` 里的协议归一化逻辑：

```js
// 路径 → file:/// URL
function tte(t){const n=t.trim().replace(/\\/g,"/");
  return /^[a-zA-Z]:/.test(n)?`file:///${n}`:n.startsWith("/")?`file://${n}`:`file:///${n}`}

// file:/// → Electron 自定义协议 local-file://（/ 与盘符统一编码）
function yDe(e){const n=e.replace(/\\/g,"/").split("/").map((r,i)=> r===""&&i===0?"": /^[a-zA-Z]:$/.test(r)?r:encodeURIComponent(r)).join("/");
  return /^[a-zA-Z]:\//.test(e)?`local-file:///${n}`: ...}

// 识别 local-file:// 与 file:// 两种前缀
function ete(t){return /^local-file:\/\//i.test(t)?g4n(t):/^file:\/\//i.test(t)?h4n(t):""}
```

还有一段把 HTML 预览里的 `src/href/poster/data` 与 `url()` 里出现的 `file://`、`C:\...` 统一改写为 `local-file:///`，保证预览 iframe 不会因混合内容被拦。

即：**卡片不是独立数据结构，而是 markdown 链接 + 自定义协议 + 协议改写**这三级组合。前端只需识别链接协议就能给出「打开/预览/定位」动作。

## 5. 与 gaea 现有实现的差距

gaea 的 `DeliverableCards.tsx`（273 行）已经比灵犀这条链路更重：

| 维度 | 灵犀 | gaea |
|---|---|---|
| 数据来源 | 正文 markdown 链接（模型必须吐对协议） | **两路合并**：正文启发式 `deliverableMentions` + 本轮产物登记表（工具写盘即登记） |
| 缺失态 | 无（链接错了就是死链） | 「未生成」徽标 + 灰度淡化（探测失败按存在处理） |
| 变更态 | 无 | 「已更新」徽标 + Office 草稿/就绪徽标（JournalList 证据链） |
| 交互 | 点击打开预览 | 整行开预览；悬停外部打开 / 定位 / 复制路径 |
| IM 通道 | `deliver_result` 工具推卡片 | 无（微信 beta 未接交付卡片） |

**结论**：gaea 不需要抄灵犀的卡片 UI，真正值得抄的是三条契约级经验：

1. **协议优先于启发式**：让模型输出 `[名称](file:///abs)`，前端按协议直取路径；启发式正则只做兜底。现在 gaea 全靠正则扫裸路径，模型换个写法就漏卡。
2. **提示词里写明渲染陷阱**：链接禁止反引号/代码块包裹、伪协议只用于用户可见链接、工具参数仍用真实绝对路径。这三条能消掉大量「卡片变成代码片段」的投诉。
3. **分场景选通道**：有 UI 的场景走链接，无 UI 的场景（IM/通知）必须走工具推送，且一次一个文件、写完文字再调工具。

若之后接微信/IM，直接把 `<im_scene>` 那套语义搬过去即可：`deliver_result(ref, 绝对路径)` + 单文件单次 + 文字写完再调。
