## 0 一页结论

**能拿的三块**（对 gaea 进度板块有直接增量）：

| # | 可蒸馏对象 | 为什么值钱 | gaea 现状 |
|---|---|---|---|
| 1 | **进度管控层**：检视时间（多期）+ 前锋线（设置/拉直/清除/历史对比）+ 冻结状态 + 预警状态机 | gaea 现在只有 `progress:number` 与基线漂移，**没有"某一时点实际做了什么"的一等模型**；这是"AI 盯计划"唯一能落地的事实底座 | 缺 |
| 2 | **检查器规则集**：11 条工作级体检提示 + 关系合法性/循环/节点连接拦截 + 分区分组关系约束 | gaea 有 DCMA 14 点（健康度），但没有"逐工作可点击定位 + 可解释"的业务级纠错 | 半（dcma.ts 只覆盖结构健康度） |
| 3 | **排网方式与约束**：越早越好/越晚越好（项目默认 + 单工作覆盖）+ 要求开始/要求完成时间 + 首日是否参与计算 | gaea 只有 auto/manual；ALAP 与 SNET/FNET 类约束是"倒排校核"的另一半 | 缺 |

不是明文 JSON/ZIP。**不要追这个格式**——互操作走 MPP / MSPDI(XML) / Excel 三条通道，
这三条斑马自己也在用（`导出XML格式，该格式可以在Project中转换打开`、`导出 MPP 失败`、`libxl.dll`）。

**成本最低的三刀**（建议按序）：§11 的 **S1 检查器** → **S2 检视+前锋线** → **S3 排网方式与约束**。

### 2.3 分区（分区 = 汇总行）与成组

实测约束（提示文案原文）：

- 分区是**工作的一种角色**（`显示为分区`/`取消显示为分区`/`至层级N设为分区`/`所有父工作设为分区`），不是独立类型；

### 3.2 日历与工期

- 内置日历不可改名（`不允许修改内置日历名称！`）、日历名不可重名；
- 项目级 `总工期(工日)` / `总工期(含假期)` 双口径并存，另印"总持续时间 %d"；
- **`首日是否参与计算-是/否`** —— 工期计数的首日约定开关（gaea 目前写死 ES=0 语义，需要这个开关做对齐）；
- 工期闸门：`不能小于等于0`、`不能小于0.01`、`不能大于9999`、`不能小于-9999`、`持续时间不能小于1天`、`持续时间不能小于10000天`（两组文案并存 = 不同字段/单位各有闸门）。

### 3.3 文件格式（实测字节结构，**不要追**）

三个本地数据文件头部同构：

```
BimDeco.gzp  9229B : 08 02 | 12 16 [08 8b dd 04 | 12 10 <16B>] | 1a f0 47 <9200B 高熵>
ResDB.gdb    5101B : 08 02 | 12 16 [...]                  | 1a d0 27 <…>
ViewDB.gdb   2989B : 08 02 | 12 16 [...]                  | 1a 90 17 <…>
```

解析：`field1 varint=2`（版本）+ `field2 22B`（嵌套：id + 16 字节标识/密钥材料）+ `field3 <len>B`。
对 field3 试过 zlib/deflate/bz2/lzma **全部失败**，字节熵极高；加解密栈为 `libcrypto-3-x64.dll`/`libeay32.dll`。
另实测字符串 `7zip保存失败`（导出包走 7z）、`json保存验证失败`、`Json数据为空，不能转换为pert对象`。

> **结论**：`.zp` 系列 = **protobuf 信封 + 加密内容体 + 内部 JSON 模型**。
> 复刻成本高、法律面不干净、且对 gaea 无产品价值（用户不会拿 .zp 喂给我们）。
> 正确通道：**MPP 导入/导出、MSPDI XML、Excel（xlsx）**——三者斑马都实现，gaea 已有 2.5 条（见 §10）。
>
> **D1 已把"加密内容体"定死**（见 `gaea-schedule-zpert8-network-re-20261114.md` §8）：
> `zpbdata.ZPertFileArgs{pert_json, images, attachments, brotli_original_size, aes_iv,
> co_edit_version, timestamp, lock_num}` —— 正文是 **JSON → brotli 压缩 → AES（`aes_iv` 单独存）**，
> 上面的 `field2` 里那 16 字节就是 `aes_iv`。结论不变：不追该格式。

## 4 计算口径（可直接实现的规则）

### 4.1 排网方式与约束

| 机制 | 实测文本 | 语义 |
|---|---|---|
| 越早越好（ASAP） | `排网方式` 列 + 各视图默认 | 前推取最早 |
| 越晚越好（ALAP） | `当前计划排网方式为越晚越好，在计划的要求开始时间和要求完成时间内无法优化到指定的资源限量值` | 后推取最晚，**与时差、资源优化耦合** |
| 项目默认 + 单工作覆盖 | `使用非默认排网方式`（可筛选/可体检） | 排网方式有继承关系，偏离默认值要能被挑出来 |
| 要求开始 / 要求完成 | `ask_start_time` / `ask_stop_time`；`计划开始早于要求开始且计划完成晚于要求完成` | 双侧约束 + 一致性检查 |
| 项目/父工作约束传导 | `“%s”任务的计划开始时间被安排在项目要求开始时间（%s）之前，您可以…` / `…在其父工作要求开始时间（%s）之前` | 约束沿 WBS 向下传导，且**自动移动 + 告知** |
| 首日约定 | `首日是否参与计算-是/否` | 计数约定开关 |
| 约束清理 | `所有有前置工作的工作/关系的要求开始时间，和所有有后置工作的工作/关系的要求结束时间` 会被一键清除 | 冗余约束治理 |

### 4.2 时差两套

- **总时差**（`总时差`）与**自由时差**（`自由时差`）都在列里；
- 额外维护 **`最晚开始(自由)` / `最晚完成(自由)`**：即用自由时差口径反推的第二套最晚时间；
- 分组维度直接支持 `分组-总时差`。

> gaea：`cpm.go` 已有 `tf/ff` 与 `freeFloatPart`，但**没有"自由时差口径的第二套最晚时间"**（`latest_start_by_free`）。
> 这是"搭接关系下自由时差 vs 总时差分别约束哪一端"的口径差异，做对齐时要补。

### 4.3 关键性四视角

1. `is_keywork` 当前关键工作；
2. `last_is_key_work` 原计划关键工作（基线对比用）；
3. `estimate_key_work` **预测关键工作**（按当前实际/预测完成重算的关键工作）；
4. `effect_on_key_path` **影响关键线路**（该工作的变化是否会推动关键线路）。

> gaea 只有 `critical` 一个布尔 + `CriticalChain()`。**预测关键工作 + 影响关键线路** 是"AI 建议改计划"必备的因果字段。

### 4.4 关系与结构检查

规则全集与判定见 §8.1（C10–C15）。要点：**阻断类规则在结构变更前预演**（上移/下移/升级/降级先算再落库），
而不是落库后报错回滚——这点与 gaea `ops.go` 的"先校验后应用"方向一致，可直接复用其事务化 `ApplyOps` 外壳。

## 5 进度管控（gaea 最大空白，优先做）

### 5.1 检视时间（多期"数据日期"）

实测规则（原文）：

| 规则 | 文案 |
|---|---|
| 检视时间不得早于项目要求开始时间 | `输入的检视时间小于项目要求开始时间，请做修改` |
| 不得与当前检视相同 | `新增的检视时间与当前检视时间相同，请修改` |
| 必须晚于上次拉直时间 | `该计划上次拉直时间为[%s]，设置的检视应在该时间之后，请重新设置` |
| 不得重复 | `新增的检视时间已存在，请勿重复增加` |
| 企业管控：实际时间不得早于管控线 | `按照企业管控要求，实际开始时间/实际完成时间不得早于[%s]之前，请填写符合要求的实际时间` |
| 实际时间与检视时间的关系参与"按原计划处理"判定 | `…小于等于检视/反馈时间（…），无法按照原计划时间处理` |

> 语义：**检视 = 一次带时间戳的进度快照**。计划是连续推演的，执行是离散打点的；两者必须分离存储。
> gaea 现在把 `progress:number` 塞在 task 上，等于"只有一张快照"，历史不可回溯、不可对比。

### 5.2 前锋线与拉直

命令面（实测）：`设置前锋线`、`尝试设置前锋线`、`系统自动设置前锋线`、`拉直前锋线`、`按原计划工期`/`按预测时间`（拉直口径）、`清除所有前锋线`、`尝试清除所有前锋线`、`历史前锋线对比分析`、`前锋线对比表`、`导出前锋线对比分析表`、`当前检视-历史检视` 差异列。

冻结语义（原文）：

- `前锋线拉直后该工作被冻结，不能将该工作的执行状态改为未开始/进行中` —— 拉直把已发生的事实**钉死**，防回改；
- `实际开始/完成时间` 与 `检视/反馈时间` 的先后决定"能否按原计划时间处理"。

**前锋线对比表列**（原文）：`原计划｜差异对比（当前检视-历史检视）｜检视时间｜工期(工日)｜累计实际完成（%）差异｜预计完成差异｜实际完成差异｜执行状态｜累计实际完成（%）｜预计完成｜解决措施｜负责人`。

### 5.3 预警状态机

| 维度 | 实测值 |
|---|---|
| 状态枚举 | `未滞后` / `未影响` / `正常` / `无级别` / 级别 `1..5` / `红灯` / `绿灯` |

> 这是 gaea 完全缺的一层，且**"两种超期算法并存且用户可切"**是斑马的专业度所在：

| 预警状态机 | 状态/档位/红绿灯/两算法 | 无 | **缺（P1）** |
| 里程碑治理 | 级别/偏差溯源/必填/附件 | `IsMilestone` 布尔 | **缺** |
| 结构检查 | C1–C15 规则集 + 可干预 | `dcma.ts` 14 点（健康度）+ `Validate` | 半（缺业务级逐条定位） |
| 关系冗余合并 | `合并多余关系` | 无 | **缺** |
| 视图（列+分组+筛选+样式快照） | 10 内置 + 自定义 + 云 | 无"视图"对象 | **缺** |
| 分组维度 | 14 种 | `ganttGroup.ts` 3 种（critical/mode/milestone） | **缺** |
| 资源均衡 / 限量优化 | 两算法 + 回执 | `usage.ts` 只算超载 | **缺（P2）** |
| 资源库/定额库（分层编码） | 外置库 + 行级校验 | 项目内 `Resources[]` | **缺（P2）** |
| 四口径单价/产值 | 计划/实际/合同/产值 | `cost.go` 标准费率 + 每次使用 | 半 |
| 期间计划/工程量 | 期间窗口 + 当期量 + 报告 | 无 | **缺（P2）** |
| 投标检查评分 | 打分 + 导出/打印 | 无 | **缺（P2）** |
| MPP 导出 | 有 | 只解析 | **缺（P1）** |
| 双代号/单代号/时标网络 | 自动布图 + 时标 + 节点编号 | `aoa.ts`/`aoaLayout.ts`（手动 pin + 前端布局） | 半（缺时标/节点编号口径） |

> **一句话**：gaea 的"计划编制 + 基线 + DCMA + 挣值 + 蒙特卡洛"已经比斑马更深；
> 但**"执行期治理"（检视/前锋线/预警/里程碑）与"视图体系"整层是空的**，
> 而这正是"agent 长驻盯工程"要落地的地方。

## 11 落地刀单（建议顺序，含验收口径）

### S1 检查器（0.5 刀，最高性价比）
- 落点：新建 `frontend/src/schedule/checker.ts`（纯函数）+ `internal/schedule/check.go` 镜像；`TaskInspector` 挂入口。
- 内容：§8.1 的 C1–C15，输出 `Diagnostic{code, severity, taskId?, linkIndex?, message, fix?}`；
  `severity ∈ {error, warn, info}`，`fix` 给"可执行动作"（如 `removeLink`/`clearAsk`/`mergeRedundant`）。
- 验收：每条规则至少 1 正 1 负用例；`ff`/`sf` 组合合法性表以 `(前置类型, 后置类型)` 为键全枚举；
  检查结果可点击定位到行（复刻 `检查-点击定位检查项`）；**结构变更（上移/降级）先跑检查再落盘**（复刻 C13）。

### S2 检视时间 + 前锋线（1.5 刀，最大增量）
- 数据：`Project.reviews: Review[]`，`Review{date(工作日序号), asOfISO, actuals:{taskId:{start?,finish?,percent}}, frozen:{taskId:true}}`；
  `Task.actualStart/actualFinish` 为"最近一次检视回填值"的派生态。
- 规则：§5.1 的四条时序校验 + 企业管控线（作为可选 `Project.controlLine`）。
- 派生：`plan_elapsed_time`/`plan_remaining_time`、`预计完成`(= predict)、`累计实际完成(%)`、`当期完成量`；
  **预测关键工作**与**影响关键线路**在"按实际/预测重算的 CPM"上取（§4.3）。
- UI：横道图叠前锋线折线（当前检视 vs 历史检视双线可选）；`前锋线对比表` 按斑马列头导出。
- 验收：拉直后该工作 `frozen=true` 且改执行状态被拒（复刻原文语义）；两次检视对比表数值与手算一致；
  检视删除不破坏其他检视的冻结集。

### S3 排网方式与约束（1 刀）
- 数据：`Project.scheduleType: 'asap'|'alap'`；`Task.scheduleType?`（覆盖）+ `Task.askStart?/askFinish?`（工作日序号或 ISO，二选一并写死）；
- 算法：`cpm.go` 增 ALAP 反向推演路径（复用 `backwardBound` 的对称实现）+ 约束夹取；
  约束传导检查（项目/父工作约束 → 子工作，复刻 §4.1 第 5 行）；
- 验收：ALAP 下"零总时差任务集合"与 ASAP 一致；有约束时 `plan_start` 被夹取且产出 `constraintApplied` 诊断（进 S1 的 diagnostic 通道）。

### S4 MPP 导出（0.5–1 刀）
- 落点：`internal/schedule/mpp_export.go`（复用现有 `mpp_layout.go` 的字段布局表反向写）。
- 口径：先支持"单项目 + 任务树 + 关系 + 日历 + 资源名"最小集；对 gaea 独有字段（自定义槽、双单位）明确丢弃并在导出回执里列出。

### S5 视图与分组扩展（1 刀）
- `views: View[]`（列集合 + 排序 + 多级分组 + 筛选 + 显示选项），`save/load/rename/delete` + 同名校验；
- 分组维度从 3 扩到斑马的 14（`duration/tf/leader/milestone/critical/group/site/status/resource/frontCount/behindCount/custom`），保留 `critical/mode/milestone` 兼容；
- 内置 3 个预设视图（计划编制 / 进度管控 / 里程碑列表），其余按需。

### S6 资源均衡（1 刀，可后置）
- `leveling(project, cpm, {maxUnits})`（工期可延长）与 `smoothing(project, cpm)`（工期锁定）两函数，返回
  `{ok, deltaDays, newFinish, offenders[], reason}` —— 回执文案照抄 §7.1（含"无法继续优化"的判定出口）；
- **与检视状态互斥**（复刻 `请尝试在非进度检视状态下使用`）。

### S7 期间计划 / 工程量 / 定额库（2 刀+，按客户需求触发）
按 §5.5 / §7.2 / §7.3 落地，先只做"期间窗口 + 当期/累计量"，定额库看是否有真实客户要。
